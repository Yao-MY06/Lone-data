## 四、项目经历

### 项目一：微服务高并发交易平台（点评业务场景的生产级改造）

**角色**：独立开发　|　**技术栈**：Spring Boot · Spring Cloud Alibaba · MySQL · Redis · RabbitMQ（或实际选定 MQ）· Docker Compose　|　**周期**：2026.10 – 2027.02

**项目简介**
基于点评类业务场景（商户 / 优惠券秒杀 / 订单）的 Java 后端项目，在原教学实现基础上完成生产级改造，聚焦三件事：有限微服务拆分、秒杀链路的一致性与可靠性、可复现的工程证据。

**核心工作**

- **有限微服务拆分**：以领域边界将系统拆分为 `user` / `shop-content` / `trade` 三个服务，Gateway 进入真实请求入口路径，Nacos 承担注册发现与配置管理，OpenFeign 完成跨服务调用（如 `trade` 获取用户与商户信息），明确超时、错误传播与降级边界；用 Sentinel 在真实链路上实际触发一次受控失败，验证调用方拿到明确结果且服务状态可检查。
- **秒杀链路深化**：实现 `Redis + Lua 原子判断 → MQ → 数据库落库` 的最薄闭环，用 Lua 原子完成资格校验、库存预扣与一人一单判断；消费端按业务幂等键实现可验证幂等，重复投递同一消息不产生重复订单与重复扣减；配置有限重试，失败消息可观察并由对账发现处理。
- **一致性与故障窗口治理**：针对「Lua 已成功、broker 尚未确认发布」这一一致性窗口，实现（本地消息表 + relay / 补偿对账，按实际选定填写）方案，并通过**实际注入进程失败**验证该窗口不会静默丢单；选型过程以 ADR 形式对比 Redis Stream 与选定 MQ 的投递语义、失败恢复与运维成本。
- **可复现工程证据**：用 Docker Compose 固化 MySQL / Redis / MQ 等依赖并配置健康检查；在固定环境（固定代码版本、JVM 参数、数据规模、压测脚本与采样方式）下形成可重复基线，两次执行保留原始结果；基于执行计划与慢查询日志定位并优化 1 条慢 SQL，同条件下保留优化前后对比；为 1 条完整调用链保存 trace，并完成 1 次真实错误的定位—修复—复验闭环。

**技术难点与解决**

- 消息发布与本地事务的原子边界如何界定、失败窗口如何闭环，是本项目最核心的可靠性问题；通过对照「本地消息表 + relay」与「事务消息」两条路径的原子边界、失败窗口与运维成本，结合实际架构取舍，并用真实故障注入验证所选方案能发现并恢复该窗口。

### 项目二：智能故障诊断与自动评测平台（Java Agent）

**角色**：独立开发　|　**技术栈**：Java · Spring Boot · Redis · MySQL · 可替换 LLM 接入层 · 混沌工程工具　|　**周期**：2026.10 – 2027（项目一验收后为主线）

**项目简介**
面向微服务稳定性的 AI 诊断系统：输入告警，系统通过受限的工具（指标 / 日志 / 链路 / 拓扑）逐步排查，输出**带证据链的根因、置信度与修复建议**；同时具备用故障注入 ground truth 自动判分的评测闭环。

**核心工作**

- **Agent 执行引擎**：以 Java / Spring Boot 实现无状态诊断调度服务与 Agent 主循环（规划 → 工具调用 → 观察 → 结论），每轮记录任务 ID、工具名、参数与结果摘要、时间与状态；任务结束返回结构化报告（根因、证据引用、置信度、未完成检查、建议），失败返回已完成中间结论与待办，不静默丢失。
- **受限诊断工具层**：实现 Prometheus 指标查询与日志 / 链路查询等多个真实可调用工具，为每个工具设定字段、时间窗、条数、服务名与超时白名单，杜绝任意 URL / SQL / 文件路径 / 代码执行；非法参数、越权主体、超时与内部失败均有稳定错误码，读工具失败无业务副作用。
- **可靠性机制**：实现最大轮次 / token 成本预算 / 墙钟超时三重护栏（触顶返回结构化未完成状态）；对同一工具与归一化参数的重复调用做检测，按 observe → steer → block → stop 分级处置；实现连续无信息增量的停滞检测与连续失败熔断；实现**声明—证据绑定**，每条根因结论必须引用 toolCallId / TraceId / 日志行号 / 指标时间窗，由程序校验引用是否可回查，无法回查的结论不得标为确认事实。
- **上下文管理**：以可插拔 `Compressor` 链实现四级上下文压缩（工具结果大小预算并落外部存储返回指针 → 规则清理较早结果 → 独立摘要调用 → 接近硬上限时阻塞新请求并按真实超长错误逐步丢弃最旧消息），阈值与保留策略均经实验记录确定。
- **故障注入与自动评测**：用混沌工具在固定环境注入故障（慢 SQL、Redis 延迟 / 连接耗尽、线程池 / 连接池打满等），注入记录直接写明预期根因、参数、起止时间与影响服务，作为 ground truth 与 Agent 结果比对；搭建 `注入 → 采集 → 诊断 → 证据校验 → ground truth 比对 → 原始结果归档 → 汇总报告` 评测流水线，记录根因 Top-1/Top-3 命中、证据可回查率、工具调用次数、重复 / 无效调用率、token 消耗与端到端耗时；通过**消融实验**分别关闭循环防护、上下文压缩、证据绑定中的一个机制，比较同一故障集上的指标变化。

**技术难点与解决**

- 大模型诊断的核心风险是「结论无据」与「循环失控」；前者通过强制声明—证据绑定 + 程序化引用校验把每条结论锚定到可回查的原始数据，后者通过轮次 / 预算护栏、重复调用检测与停滞熔断共同约束；并用故障注入的 ground truth 做自动判分，避免用同一个模型评判自己的答案。
