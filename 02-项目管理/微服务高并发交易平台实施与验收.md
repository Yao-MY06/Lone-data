# 微服务高并发交易平台实施与验收计划

> **定位：双项目规划中项目一的阶段实施与验收页，不是日常入口。** 本计划把原黑马点评生产级改造的最小可验证链路迁移为“微服务高并发交易平台”的首个实施切片；完整目标、业务域和研究/求职叙事以 [[大厂实习级双项目规划|大厂实习级双项目规划]] 为准。本页仍保留原方案的基线前置、标准门、收缩门、证据和候选技术纪律。日常动作只回到 [[../00-收件箱/00-当前状态面板|当前状态面板]]，立项和验收遵循 [[项目SOP|项目 SOP]]。

## 一、项目定位与硬约束

- 类型：Java 后端实习作品项目；目标是形成可运行、可解释、可复现的工程证据，不是堆叠中间件名词。
- 当前状态：未开始。先完成原版黑马点评基线，再进入本平台实施；两阶段分别验收。
- 升级前置门：原版核心链路没有实际跑通，或不能解释 Redis 缓存、锁、Lua 原子性、消息处理与 Redis Stream 原实现时，生产级改造不得开始。
- 技术启用原则：一项技术必须对应已观察的问题、真实调用需求或明确验收；只有依赖、配置、空壳服务或设计图不算完成。
- 事实边界：选定的课程仓库、分支、提交、JDK、框架与依赖版本在开工后据实登记。源版本差异、缺失功能和无法确认的行为统一写“未知”或“当前源版本未发现”，不得按其他教程记忆补写。
- 指标边界：没有固定环境和原始结果时，不得编造 QPS、P99、提升比例、成本节省、可靠性或规模结论。

### 2.2 基线范围与二值验收

下列范围以所选课程源版本的实际实现为准。若某能力在源版本中不存在，必须保存版本和检索证据，并明确标记“当前源版本不包含”；不得伪造实现，也不得把未核实的差异写成已完成。

| 基线能力 | 必须观察和解释的内容 | 最低验收证据 |
| --- | --- | --- |
| 登录 | 登录态如何生成、保存、校验和传递；受保护接口如何取得当前用户 | 一次登录成功请求及一次受保护接口调用，附响应和关键日志 |
| 商户缓存 | cache miss、cache hit、缓存更新或失效路径；穿透、击穿、雪崩的边界 | 同一商户的 miss 与 hit 各一次，附 Redis、数据库或日志对照 |
| 优惠券秒杀 | 资格判断、库存、一人一单和订单状态如何衔接 | 一次成功秒杀及 Redis、消息处理或数据库中的结果核对 |
| Redis 锁 | 加锁、释放、超时、误删风险及所用实现的所有权校验边界 | 对应源码位置、一次相关调用或测试、书面机制说明 |
| Lua | 哪些判断被合并为原子操作，键和值如何传入，脚本返回值如何驱动后续流程 | 脚本源码位置、一次执行结果、库存不足或重复下单至少一个拒绝证据 |
| 消息处理 | 生产、消费、确认、失败、积压与恢复在原实现中如何处理 | 一次消息从产生到处理结果的日志或查询链；失败能力不存在时明确记录 |
| Redis Stream | Consumer Group、pending list、确认和异常恢复的原实现边界 | 对应源码与 Redis 查询；能说明它为何适合或不适合后续需求 |
| Feed | 发布、收件箱或时间线读取方式，推或拉的实际选择 | 一次发布与一次读取调用，或经版本证据确认的缺失记录 |
| GEO | 地理数据写入、距离或附近查询及返回排序 | 一次实际 GEO 查询及 Redis/响应证据，或经版本证据确认的缺失记录 |
| 签到 | Bitmap 等实际数据结构、位偏移与连续签到计算 | 一次签到和一次查询结果，或经版本证据确认的缺失记录 |

## 三、生产级改造只承诺三个方向

实施顺序固定为：`基线通过 -> 固定环境与基线测量 -> 最小服务调用 -> Lua 到 MQ 到落库 -> 故障与幂等验证 -> 诊断与索引证据 -> 总验收`。三方向可以共享环境，但不得用一个方向的配置文件代替另一个方向的运行证据。

### 3.1 方向一：有限微服务拆分

**目标**

用最少的服务边界展示领域划分、真实服务调用和失败治理，只拆分对当前业务有意义的 `user`、`shop/content`、`trade`，避免把单体机械切碎。

**范围**

- Gateway 进入真实入口请求路径，路由到三个领域服务的实际接口。
- Nacos 只用于当前服务实际需要的注册发现或配置管理，并保存被读取或变更生效的证据。
- OpenFeign 只用于至少一条真实跨服务调用，例如 `trade` 获取用户或商户信息；必须说明超时、错误传播和降级边界。
- Sentinel 只保护已跑通的真实接口或调用链；实际触发一次限流、熔断或降级中的一种，并核对客户端结果与服务日志。
- 服务间只传递明确的请求或响应契约，记录调用失败时订单或业务状态如何处理。

**不在范围**

- 不承诺全量迁移原版业务、拆出更多服务、统一改造全部接口或建设完整配置治理平台。
- 不为展示组件而创建没有业务、没有调用方或没有失败路径的空壳服务。
- 不在本方向引入服务网格、K8s 或复杂分布式事务框架。

**最低必验收**

- [ ] Gateway 已进入真实请求路径，`user`、`shop/content`、`trade` 各至少有 1 个真实接口可调用。
- [ ] 至少 1 条跨服务调用链从入口到结果完整跑通，且 OpenFeign 的实际调用可从日志或 trace 识别。
- [ ] Nacos 的实际注册发现或配置读取可核对；不是只有依赖和配置文件。
- [ ] Sentinel 在上述真实链路上实际触发一次受控失败，调用方收到明确结果，服务状态可检查。
- [ ] README 说明为什么这样拆、边界代价、调用失败方式和仍未解决的耦合。

**可延期项**

全量业务迁移、全部配置治理、更多服务和接口、所有接口的治理规则、更多故障场景与完整容量规划。

**证据位置**

`README.md#有限微服务拆分`、`docs/evidence/services/`、`docs/architecture/service-boundaries.md`，以及 trace 系统中按测试时间或 trace ID 可复查的记录。每条证据需标注环境、请求、预期、实际结果和对应版本。

### 3.2 方向二：秒杀链路深化

**目标**

跑通 `Redis Lua -> MQ -> 数据库落库` 的最薄闭环，并通过重复消息和真实故障证明幂等、重试或对账能力，使订单在可解释的边界内达到最终一致，而不是只把 Redis Stream 换成另一个 MQ。

**范围**

以下均为待实施范围，不代表当前已经完成：

- Redis Lua 原子完成实际需要的资格、库存和重复下单判断，明确脚本成功与拒绝返回值。
- Lua 成功后进入选定 MQ，消费者完成数据库落库；记录消息标识、业务幂等键、订单状态和确认时机。
- 对“Lua 已成功，但 broker 尚未确认发布”窗口，必须结合选定 MQ 和当前架构选择并实现一种可恢复方案，例如 Redis 待发送记录与 relay、经过验证的事务消息适配，或能发现并补发的补偿/对账流程；方案、原子边界与未覆盖窗口必须据实写入 ADR。
- 消费端实现可验证的幂等：同一业务消息被实际重复投递时，不产生重复订单或重复扣减。
- 根据选定 MQ 的真实能力配置有限重试；重试仍失败时，必须有可观察的失败记录，并由人工或定时对账发现和处理不一致。
- 定义 Redis 预扣、消息状态、数据库订单和库存之间的最终一致性边界，写清不可自动恢复时的人工处理方式。

**Redis Stream 与选用 MQ 的取舍任务**

选型前先基于已观察需求填写 ADR，不预设 RocketMQ、RabbitMQ 或 Kafka 一定优于 Redis Stream：

| 真实需求 | Redis Stream 需验证 | 候选 MQ 需验证 | 决策证据 |
| --- | --- | --- | --- |
| 当前团队与部署复杂度 | 现有 Redis 是否已足够、运维边界是什么 | 新增 broker、客户端和监控的实际成本 | Compose 启动、故障恢复与操作记录 |
| 确认、重试与失败消息 | pending、claim、ack 和消费者故障是否满足恢复要求 | ack、重试、死信或延迟能力是否确实被使用 | 制造失败后的消息与消费状态 |
| 投递语义与幂等 | 重复投递发生方式和业务键选择 | 所选 MQ 的投递语义及重复来源 | 同一消息重复投递的数据库结果 |
| 顺序、积压与扩展 | 当前链路是否真的要求顺序或更大吞吐 | 所选 MQ 的能力是否对应实测瓶颈 | 固定环境的原始测量，不写推测数字 |

ADR 结论必须包含“为什么保留或替换 Redis Stream”“新增复杂度”“当前未解决风险”。选用 MQ 未经实际接入和故障验证前，只能写候选，不能写已完成升级。

**不在范围**

- 不承诺削峰数字、固定 QPS/P99、全局 exactly-once 或绝对不丢消息。
- 不承诺令牌桶、结果实时通知、复杂分布式事务平台、多机房容灾或全自动补偿。
- 不用只发送一次正常消息证明幂等，也不用单元测试桩代替真实 broker 故障。

**最低必验收**

- [ ] `Redis Lua -> MQ -> 数据库落库` 完整跑通，能用消息记录和数据库查询核对同一业务订单。
- [ ] 实际投递 1 次重复消息，数据库中没有重复订单或重复扣减，并能指出命中的幂等键与处理分支。
- [ ] 实际制造 1 次消费或落库失败，证明重试成功，或证明对账能发现并处理不一致。
- [ ] 实际注入 1 次“Lua 成功后、broker 确认前进程失败”：终止或等价阻断发布进程，保存 Lua 结果、进程失败、broker 状态与数据库状态；所选可靠发布、补偿或对账方案必须能发现该业务并完成补发或恢复，证明该窗口不会静默丢单。
- [ ] 选型 ADR 已用真实需求比较 Redis Stream 与选用 MQ，写清一致性边界、代价和剩余风险。
- [ ] README 给出复现正常、重复、消费/落库失败和发布窗口失败四条路径的最小步骤。

若“Lua 成功后、broker 确认前进程失败”尚未通过真实故障注入闭合，只能标记“已识别一致性窗口”。此时本方向最低验收未通过，生产改造标准门不得通过，README、简历和面试陈述均不得声称已经实现最终一致。

**可延期项**

令牌桶、延迟队列、秒杀结果通知、更多故障注入、自动化补偿、对账调度平台和更高吞吐优化。

**证据位置**

`README.md#秒杀链路`、`docs/adr/mq-selection.md`、`docs/evidence/seckill/normal/`、`docs/evidence/seckill/duplicate/`、`docs/evidence/seckill/recovery/`、`docs/evidence/seckill/publish-gap/`。原始 Lua 结果、待发送或补偿记录、消息、日志和数据库查询需能通过订单号、业务幂等键或消息 ID 相互对应。

### 3.3 方向三：可重复工程证据

**目标**

在固定且已记录的环境中形成可重复基线，以真实慢 SQL、索引、trace、指标和诊断证据解释瓶颈与故障；Docker Compose 负责复现当前链路依赖，不包装成尚未具备的生产运维能力。

**范围**

- Docker Compose 启动当前验收链路必需的 MySQL、Redis、选定 MQ 及实际需要的注册或观测依赖，并提供健康检查。
- 压测前固定代码版本、机器或容器资源、JVM 参数、数据规模、脚本、并发模型、预热、持续时间和采样方式；保存原始输出。
- 使用数据库执行计划、慢查询日志或实际等价证据定位 1 条慢 SQL，说明索引选择，并在同一环境和数据条件下保留调整前后结果。
- 为 1 条完整真实调用链保存 trace；采集能解释当前问题的最小指标，并让日志可按 trace ID、订单号或消息 ID 关联。
- 记录至少 1 次错误的现象、定位过程、根因、修复或处置和复验结果。

**不在范围**

- 不承诺完整可观测平台、生产级高可用、跨机房容灾、全链路压测平台或 K8s 发布体系。
- 不把不同机器、数据量、脚本或代码版本的结果直接比较为“提升”。
- 不把单次截图、平均值或工具生成的摘要单独当作性能结论。

**最低必验收**

- [ ] Docker Compose 能启动当前链路必需的 Redis、MySQL、MQ 等依赖，并保存启动、版本与健康检查记录。
- [ ] 在固定且记录完整的环境中形成 1 组可重复基线；第二次执行使用相同输入与方法，并保留两次原始结果。
- [ ] 保存 1 条从 Gateway 或入口到数据库或最终结果的完整 trace。
- [ ] 保存 1 个慢 SQL 的执行计划、索引依据及同条件调整前后证据；不能证明改善时如实写“无改善”或“未知”。
- [ ] 保存 1 次真实错误诊断闭环，且 README 能指向其日志、指标、trace 或数据库证据。

**可延期项**

更多 trace 覆盖、更多慢 SQL 和索引优化、完整监控仪表盘、长期容量趋势、自动告警、持续压测与更广运维平台。

**证据位置**

`README.md#工程证据`、`compose.yaml`、`docs/evidence/environment.md`、`docs/evidence/load-test/`、`docs/evidence/sql/`、`docs/evidence/trace/`、`docs/evidence/diagnostics/`。所有结果必须能回到代码版本、环境、输入、方法和原始输出。

## 四、阶段门与范围收缩

### 4.1 标准门

三个方向的“最低必验收”全部通过，且 README 能解释每项改造的原因、代价、失败方式和未解决风险，才可标记“生产级改造标准门通过”。任一证据缺失即为未通过；特别是发布窗口只做到“已识别一致性窗口”、尚未证明恢复时，标准门必须保持未通过，也不得声称最终一致。模块、依赖、配置、设计图或计划不等同于运行结果。

### 4.2 实施中期检查与范围冻结

在项目一实施窗口约过半时完成一次二值检查，不因文档、依赖或空壳模块数量推迟。具体日期随前置阶段的实际通过日顺延，只根据以下已发生事实决策：

- 已跑通的服务链：Gateway 是否进入真实请求，最小跨服务调用是否已有结果和失败证据。
- 已跑通的 MQ 链：`Redis Lua -> MQ -> 数据库落库` 已到哪一段，消息与数据库是否能关联。
- 失败注入：重复消息、消费或落库失败，以及“Lua 成功后、broker 确认前进程失败”分别是否有真实结果。
- 剩余工时：按尚缺验收项逐项估算可用工时、依赖和风险，不用计划完成率或主观信心代替。

检查结论只允许二选一并写入 README 或阶段记录：

1. **继续标准门**：已有最小服务链和 MQ 链，关键失败窗口有可执行方案，且剩余可用工时足以逐项完成标准门；仍不得加入候选技术或新的广度项。
2. **冻结收缩范围**：任一关键链路未跑通、发布窗口没有可执行闭合方案，或剩余工时不足时，立即冻结为下节五项收缩门。冻结后候选技术、额外服务、全量迁移、更多治理规则和其他广度不再进入本目标窗口。

冻结决定可以进一步删除范围，但不得重新扩回标准门，也不得删除收缩门五项中的任何一项。若中期检查未按时完成，默认执行“冻结收缩范围”。

### 4.3 目标窗口末的收缩门

若路线图目标窗口末标准门仍未通过，立即停止增加广度，只保留以下五项：

- [ ] 至少 1 条经过 Gateway 的 `trade` 真实调用链，入口、最小跨服务调用和结果均有证据。
- [ ] 最薄的 `Redis Lua -> MQ -> 数据库落库` 链路可运行，消息与数据库结果可核对。
- [ ] “实际重复投递并证明幂等”和“实际制造失败并证明重试恢复或对账发现并处理”至少完成 1 项。
- [ ] 固定环境下有 1 组可重复基线证据，记录环境、输入、方法和原始结果。
- [ ] Docker Compose 能启动收缩链路必需的 Redis、MySQL、MQ 等依赖，并有启动与健康检查记录。

五项全部满足才可标记“收缩门通过”。仅有服务调用，或仅有正常秒杀链路，均不能通过。通过后只能表述为“收缩版范围完成”，并逐项延期三域完整迁移、幂等或失败恢复中未完成的另一项、更多 trace 和慢 SQL/索引证据；不得声称标准门或全部生产级改造已完成。

## 五、候选技术池（默认不启用）

候选项不进入当前待办，也不阻塞标准门或收缩门。只有当前承诺链路已形成证据、观察到明确问题、候选技术能直接解决该问题，并先写出验收与退出条件时，才可启用；一旦中期检查冻结收缩范围，本目标窗口内不得启用任何候选项。

| 候选类别 | 基于观察证据的启用条件 | 启用前必须回答 |
| --- | --- | --- |
| Caffeine + Redis 多级缓存 | 固定环境测量显示数据库读取或远程 Redis 访问是当前主要瓶颈，且数据一致性和失效要求可定义 | 本地缓存命中、失效、容量和一致性如何验证；为何单层 Redis 不够 |
| Bloom Filter | 已观察到大量不存在 key 穿透缓存并造成可量化的数据库压力，且误判可接受 | 数据如何装载和更新；误判、漏更新与回退查询怎样处理 |
| Elasticsearch 复杂搜索与高亮 | 出现 MySQL 难以满足的真实多条件、全文检索、相关性排序或高亮需求，并有查询样例与验收 | 索引映射、分页、相关性和高亮如何验证；简单数据库查询为何不够 |
| Canal + MQ 数据同步 | Elasticsearch、缓存或其他读模型已启用，且实际双写方案暴露一致性或耦合问题 | 全量初始化、增量顺序、重复、延迟、失败恢复与对账如何验证 |
| XXL-Job 预热或对账 | 已存在必须跨实例调度的预热或周期对账任务，单实例定时任务的重复执行、可靠性或管理问题已复现 | 分片、幂等、失败重试和错过调度如何处理；为何简单任务不足 |
| WebSocket / SSE | 用户确有实时接收秒杀结果的需求，轮询的延迟或资源问题已被观察 | 连接鉴权、断线重连、消息遗漏和水平扩展如何验证；选择 WebSocket 还是 SSE |
| Feed 推拉结合、排序与冷热分离 | 真实数据或测试模型显示单一推/拉模式在大 V、读放大、写放大、排序或存储上触及边界 | 关注关系与热点分布是否可信；推拉切换、排序正确性和冷热迁移如何验收 |
| ShardingSphere 分库分表或读写分离 | 单库在固定环境、真实索引和查询已优化后仍达到已测容量或读写瓶颈 | 分片键、跨分片查询、扩容、事务、一致性和故障恢复如何验证 |
| K8s | Compose 已不足以满足经过确认的多实例编排、滚动发布、弹性或环境治理需求，并有可用部署环境 | 健康检查、配置、资源、发布、回滚和持久化如何验收；新增运维成本由谁承担 |
| 智能探店 Agent、多模态或 RAG | 核心后端已闭环，且有明确用户任务、真实数据边界和不可由普通搜索解决的需求 | 模型输入、检索质量、权限、隐私、成本、失败回退和评测集如何验证 |

候选技术启用后必须进入独立小里程碑；若验收不能证明它解决了已观察问题，删除或回退，不为简历关键词保留。

## 六、证据与简历规则

### 6.1 证据最小格式

每份证据至少记录：日期、代码版本、环境与依赖版本、输入或请求、执行方法、预期、原始结果、结论、限制和复现命令。截图只能辅助说明，不能替代日志、trace、消息状态、数据库查询或原始压测输出。

建议在 README 建立“主张 -> 证据”索引：

| 可写主张 | 最低证据 |
| --- | --- |
| 完成有限拆分 | Gateway 真实请求、跨服务调用或 trace、Nacos/Sentinel 实际使用记录 |
| 完成异步秒杀链路 | Lua 结果、MQ 消息、消费日志和数据库订单可按同一业务标识对应 |
| 具备幂等或恢复能力 | 实际重复消息或真实失败场景及最终数据库状态 |
| 分析并处理慢 SQL | 执行计划、索引依据、同条件原始结果和限制 |
| 形成可重复基线 | 完整环境、脚本、输入、两次原始输出和差异说明 |

### 6.2 简历事实门

- 简历条目只在对应最低验收完成后编写，并链接到可复现证据；计划、学习过、接入依赖或画图不能写成完成。
- 只描述本人实际实现和验证的范围。团队规模、流量规模、业务价值和生产可靠性没有来源时写“未知”或不写。
- 不得编造 QPS、P99、并发量、提升比例、延迟降低、成本节省、故障恢复时间、可用性或吞吐结论。
- 性能数字必须同时给出环境、数据规模、脚本、采样方法和原始结果；比较必须保持关键条件一致。否则只写验证方法和发现，不写效果数字。
- 收缩门通过时，只能写收缩版事实；未完成的服务、保障和工程证据不得通过措辞包装成标准门完成。

## 七、面试复盘问题

完成对应证据后，用当前代码和日志回答；无法用项目事实支撑时直接写“尚未验证”。

1. 为什么要拆 `user`、`shop/content`、`trade`？哪些耦合仍留在原处，为什么没有继续拆？
2. 一次请求从 Gateway 到结果经过哪些服务？Nacos、OpenFeign、Sentinel 分别在哪个真实环节起作用？
3. 跨服务调用会在哪里失败？超时、重试、降级如何影响调用方和业务状态？
4. Lua 成功但消息未发送、消息已发送但落库失败、落库成功但确认失败时，各自如何发现与处理？
5. 幂等键为什么这样选？重复消息、并发消费和消费者重启时如何证明不会重复下单或扣减？
6. Redis Stream 与选用 MQ 的取舍依据是什么？新 MQ 解决了哪个已验证问题，又带来什么部署和一致性成本？
7. 固定环境下当前瓶颈是什么？证据如何排除脚本、网络、数据量或 JVM 状态造成的误判？
8. 慢 SQL 为什么选择该索引？执行计划发生了什么变化，哪些场景可能让索引失效？
9. 当前 trace、指标和日志能定位哪些故障，仍有哪些盲区？
10. 这个项目离真实生产系统还缺什么？剩余最大的可靠性、安全、容量和运维风险分别是什么？
