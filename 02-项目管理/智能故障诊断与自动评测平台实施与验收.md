# 智能故障诊断与自动评测平台实施与验收计划

> **定位：双项目规划中项目二的阶段实施与验收页，不是日常入口。** 本项目是 Java 实现的后端稳定性工程系统与可靠性研究项目，依赖项目一“微服务高并发交易平台”形成可观测数据源后再正式启动。完整目标、研究叙事和候选方向以 [[大厂实习级双项目规划|大厂实习级双项目规划]] 为准；当天动作只维护在 [[../00-收件箱/00-当前状态面板|当前状态面板]]。

## 一、项目定位与硬约束

- **目标问题：** 输入微服务告警，系统通过指标、日志、链路和拓扑工具逐步排查，输出带证据链的根因、置信度和修复建议，并能用故障注入产生的 ground truth 自动判分。
- **技术边界：** Java/Spring Boot 承载诊断服务、Agent Loop、工具权限、状态和评测；模型通过可替换的 LLM 接入层调用。Python 或 DeerFlow 只有在真实需求和版本证据确认后才可作为外部编排入口，不是本项目完成的前置条件。
- **完成边界：** 设计图、提示词、依赖、模拟响应、单元测试桩和一次正常演示都不能代替真实故障注入、真实工具调用、证据校验和重复评测。
- **状态：** 未开始。项目一未形成可观测数据源、未完成项目二简报和范围冻结前，本项目不抢占唯一开发 P0。
- **事实边界：** 所有模型、框架、故障工具、环境和指标版本开工时登记；未知项写“未知”，不得按教程或附件示例补成事实。
- **指标边界：** 不编造根因准确率、pass@1、pass^k、token 成本、耗时、重复率、幻觉率或性能提升。每个数字必须绑定固定环境、故障集、模型版本、样本数、脚本和原始输出。

## 二、研究与工程主线

实施顺序固定为：

`项目一可观测数据源 -> Claude Code 机制资料整理 -> 诊断服务骨架 -> Agent Loop -> 工具与证据链 -> 循环防护与上下文压缩 -> 故障注入 -> 自动评测 -> 消融与复盘`

### 2.1 研究产出

形成《Claude Code 可靠性机制逆向分析》技术报告，范围只包括：Agent 主循环与停止条件、工具输入/权限/结果预算、四级上下文压缩、子代理或上下文隔离。资料是研究输入，不是 Claude Code 内部事实的替代证据；引用版本、来源和无法核实处必须登记。

### 2.2 工程架构

```text
告警 Webhook / 定时巡检
        |
诊断调度服务（Spring Boot，无状态）
        |
Agent 执行引擎：规划 -> 工具调用 -> 观察 -> 结论
  |       |             |
  |       |             +-- 证据绑定、置信度和报告校验
  |       +---------------- 指标 / 日志 / Trace / 拓扑受限工具
  +------------------------ Redis 会话状态与任务状态
                              |
                      MySQL 诊断记录 + ES 证据检索（按需）
                              |
                  故障注入 -> 采集 -> 诊断 -> ground truth 比对 -> 报告
```

默认先实现最薄单体服务和少量受限工具；只有观测到跨实例、异步削峰或检索瓶颈，才分别评估 MQ、Gateway、K8s、ES 等候选能力。不得为架构图创建空壳服务。

## 三、最小承诺范围

### 3.1 Agent Loop

- [ ] 有一个可运行的 Java 诊断任务接口，能完成至少一轮“选择工具 -> 接收结果 -> 形成中间观察 -> 输出结论”。
- [ ] 每轮记录 task ID、工具名、参数摘要、结果摘要、时间和状态；敏感正文、令牌、连接串和完整日志默认不写入审计记录。
- [ ] 任务结束返回结构化报告：根因、证据引用、置信度、未完成检查和建议；失败返回已完成中间结论与待办，不静默丢失。

### 3.2 受限诊断工具

至少选择两个真实可调用工具，默认从以下范围选择：Prometheus 指标查询、日志检索、SkyWalking 链路查询、服务拓扑查询。每个工具必须有字段、时间窗、条数、服务名和超时白名单；禁止任意 URL、任意 SQL、任意文件路径和任意代码执行。

- [ ] 合法调用能返回带来源标识的结果。
- [ ] 非法参数、越权主体、超时和内部失败均有稳定错误码或等价错误模型。
- [ ] 读工具失败无业务副作用；工具结果过大时截断并返回可复查的证据指针。

### 3.3 可靠性机制

首版至少实现并单独验证：

1. 最大轮次、token/成本预算和墙钟超时；触顶返回结构化未完成状态。
2. 同一工具与归一化参数的重复调用检测，按 observe -> steer -> block -> stop 分级处置。
3. 连续无信息增量的 stall detection。
4. 压缩或恢复操作连续失败 3 次熔断，并记录熔断原因。
5. 声明-证据绑定：每条根因结论引用 toolCallId、TraceId、日志行号或指标时间窗；程序校验引用是否存在，无法回查的结论不得标为确认事实。

### 3.4 上下文管理

以可插拔 `Compressor` 链实现最小版本：

- L1：工具结果大小预算，超限落外部存储并返回指针；
- L2：规则驱动清理较早工具结果；
- L3：必要时使用独立摘要调用生成结构化摘要；
- L4：接近硬上限时阻塞新请求，并在真实超长错误后逐步丢弃最旧消息。

阈值、保留条数和摘要结构必须通过实验记录；附件中的 83.5%、20K、13K、p99.99 等数字只能作为待验证假设，不能直接写成项目结果。

## 四、故障注入与自动评测

### 4.1 Ground truth 原则

故障由 ChaosBlade、Chaos Mesh 或等价工具在固定环境中注入，注入记录直接写明预期根因、参数、开始/结束时间和影响服务。Agent 诊断结果与该记录比对，避免用同一个模型判断自己的答案。

### 4.2 首批故障集

先选择 3 个能在项目一真实环境复现的场景：慢 SQL、Redis 延迟或连接耗尽、线程池/连接池打满。只有首批闭环稳定后，才扩展到 MQ 堆积、Pod kill、网络丢包、缓存击穿、CPU 飙高等场景。

### 4.3 评测指标

每次评测至少保存：任务成功/失败、根因 Top-1/Top-3 是否命中、证据引用是否可回查、工具调用次数、重复调用率、无效调用率、token 输入/输出、端到端耗时和错误类型。重复运行同一任务时记录 pass@1 与 pass^k；样本不足或条件不一致时写“未知”。

### 4.4 评测流水线

`注入 -> 采集 -> 诊断 -> 证据校验 -> ground truth 比对 -> 原始结果归档 -> 汇总报告`

- [ ] 正常路径和至少一个失败路径可重复运行。
- [ ] 报告能关联故障 ID、任务 ID、工具调用 ID、代码/模型版本和原始输出。
- [ ] 消融实验能分别关闭循环防护、上下文压缩、证据绑定中的一个机制，并比较同一故障集上的变化。

## 五、安全、状态与证据边界

- 认证主体、会话和故障任务由服务端绑定；不得信任客户端提交的 `userId`、`tenantId` 或资源所有者。
- 无凭据或无法认证返回 `UNAUTHENTICATED`；已认证但无权返回 `PERMISSION_DENIED`；主体 A 不得读取主体 B 的会话、报告、证据或产物。
- Redis 只存短期任务/会话状态；MySQL 保存可跨重启读取的诊断记录。若使用 ES，只保存可检索证据，不把它当唯一事实源。
- 失败注入必须核对二值不变量：读工具无副作用、状态写入无半写入、报告无无证据结论、超时不伪装为成功。
- 日志和报告不得泄露密钥、连接串、绝对路径、SQL、完整敏感正文或内部堆栈；证据脱敏不能破坏任务 ID、调用 ID 和故障 ID 的关联。

每份证据至少记录：日期、代码/配置/模型版本、环境、故障参数、输入、执行方法、预期、原始结果、结论、限制和复现命令。截图只能辅助，不能代替原始日志、指标、链路、数据库查询或评测输出。

## 六、阶段门与范围收缩

### 6.1 启动门

- [ ] 项目一已有可复查的可观测数据源或明确的脱敏测试环境。
- [ ] 项目二一页简报写清用户/问题、交付物、截止窗口和 15 分钟第一步。
- [ ] 首批两个工具、三个故障场景和证据目录已冻结。

### 6.2 第 7 个实际开发日中期冻结

只根据真实结果二选一：

1. **继续标准范围：** Agent Loop、至少两个工具和一个故障注入场景已跑通，证据可关联，剩余时间足以完成证据绑定与自动评测。
2. **冻结收缩范围：** 任一关键链路未跑通或剩余时间不足时，只保留一个诊断接口、两个工具、一个故障场景、证据校验和一次可重复评测；删除新增工具、更多故障、候选中间件和研究扩展。

未按时检查时默认执行收缩范围。收缩范围通过只能写“已验证切片”，不得称完整平台、生产级 RCA 或研究结论完成。

### 6.3 最终阶段门

- [ ] Agent Loop 正常和受控失败路径均可运行。
- [ ] 至少两个受限工具有合法、非法、越权或超时证据。
- [ ] 至少一个故障场景有 ground truth、诊断报告和程序化证据校验。
- [ ] 至少一个可靠性机制和一个消融对照有原始评测结果；无结果的指标写“未知”。
- [ ] 任务、工具、故障、报告、版本和原始输出可互相追溯。
- [ ] README 说明架构、边界、失败语义、复现方式、已知限制和未完成候选项。

任一项缺失即未通过。不得用代码行数、架构图、课程观看、模型名称或一次演示替代阶段门。

## 七、候选技术池（默认不启用）

以下内容吸收附件和原 DeerFlow 方案，但均不进入当前待办：

| 候选能力 | 仅在什么证据出现后考虑 |
| --- | --- |
| Elasticsearch 证据检索 | 日志/证据规模和查询样例证明普通存储不足 |
| RocketMQ/Kafka 诊断任务总线 | 同步诊断出现已测削峰、重试或解耦限制 |
| K8s 多副本 | Compose 无法满足已确认的多实例、滚动发布或资源治理需求 |
| 向量检索（PGVector/Milvus） | 固定评测集证明关键词检索召回不足 |
| 记忆压缩与长期知识库 | 真实会话或故障复盘出现已测上下文/存储限制 |
| 多租户平台 | 基本主体隔离完成后出现真实租户、配额或审计需求 |
| Java Docker 代码沙箱 | 真实任务必须执行不可信代码且安全验收可行 |
| Gateway、Sentinel、实时 SSE/WebSocket | 工具调用量、过载或实时进度需求有实测证据 |
| 更多 Agent、DAG、调度和模型对比 | 首版评测闭环完成且出现明确复杂度瓶颈 |

一次只启用一个候选能力；启用前写清问题、验收、退出条件和新增风险。不能证明解决已观察问题时删除或回退。
