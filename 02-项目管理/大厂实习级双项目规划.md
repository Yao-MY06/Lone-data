## 一、项目一：微服务高并发交易平台（主菜）

后端面试官的判断标准：你解决了什么分布式/高并发难题、怎么权衡的、数据指标是什么。"我用了这些组件"等于零分，"我为什么这样选、踩过什么坑、优化前后数据如何"才是得分点。

### 1.1 业务域：复杂度要够，不能只是"下单"

```
网关层：Spring Cloud Gateway（限流、鉴权、防刷、秒杀 URL 动态化）
  ├─ 用户服务（登录态、风控黑名单）
  ├─ 商品服务（商品详情、活动预热、热点数据）
  ├─ 营销服务（优惠券、满减、优惠计算与互斥规则）
  ├─ 库存服务（热点库存扣减，并发主战场）
  ├─ 购物车服务（合并下单、价格快照）
  ├─ 订单服务（订单状态机、异步下单、超时关单）
  ├─ 支付服务（支付回调、幂等）
  └─ 对账服务（T+1 三方对账、差错处理）← 差异化亮点
```

中间件：Nacos + Sentinel + Seata + RocketMQ + Redis Cluster + MySQL（主从读写分离）+ ShardingSphere（订单分库分表）+ Caffeine 本地缓存。

**订单状态机要显性实现**：待支付 → 已支付 → 履约中 → 已完成 / 已取消 / 退款中，状态迁移用状态模式封装，非法迁移直接拒绝。

### 1.2 技术深度清单（每一点都要能回答"为什么 / 踩过什么坑 / 数据对比"）

**① 分层过滤与防刷**
前端置灰 → 网关限流 → Sentinel 接口级 QPS 限流与熔断 → 秒杀 URL 动态化 → 验证码 → 黑名单。深挖点：每层拦截的粒度与成本。

**② 缓存体系（读链路）**
- Cache Aside + 缓存空值/布隆过滤器防穿透、逻辑过期防击穿、随机过期 + 永不过期热 Key 防雪崩——三大经典问题逐个给出实现；
- 多级缓存：Caffeine 本地缓存（热点商品详情）→ Redis → DB；
- 缓存一致性：延迟双删 vs Canal 订阅 binlog 异步刷新，讲清双删的时序窗口坑和 Canal 的兜底。

**③ 库存扣减（写链路，并发主战场）**
- Redis Lua 原子化"查 + 扣"，杜绝超卖；
- 热点 Key 拆分到 Cluster 多节点；卖不完时子 Key 库存回收；
- 深挖点：为什么不用 DB 乐观锁直接扣（行锁热行瓶颈）？Redis 扣成功但下单消息没发出去怎么办（引出可靠消息）？
- 分布式锁对比：Redis + Lua / Redisson（看门狗续期）vs ZooKeeper 锁（CP、性能低），说明不同场景的选择。

**④ MQ 削峰与可靠消息**
- 抢中即返回"排队中"，RocketMQ 异步下单削峰；
- 可靠投递：本地消息表 vs RocketMQ 事务消息，实现一种并对比另一种；
- 消费幂等：唯一键去重表 / Redis 去重；
- 顺序消息：同一订单的状态流转消息按订单 ID 哈希到同一队列；
- 消息积压预案：扩容、降级、临时代偿。

**⑤ 幂等体系**
- 下单防重：前端 token + 服务端唯一索引双保险；
- 支付回调幂等：回调可能重复 N 次，以支付流水号做状态机前置校验 + 唯一约束兜底。

**⑥ 分布式事务**
- 下单（订单库 + 库存库 + 优惠券核销）：Seata AT 实现，同时能讲 TCC 与本地消息表最终一致性的取舍（性能、侵入性、适用场景）。

**⑦ 超时关单与库存/券回补**
- RocketMQ 延迟消息 vs Redisson DelayedQueue vs 定时轮询，三方案对比选型；
- 回补要考虑：Redis 库存、DB 库存、优惠券、子 Key 再平衡。

**⑧ 对账系统（差异化亮点）**
- 支付流水 vs 平台订单 vs 库存变更三方对账：对账文件拉取、双向核对、长短款差错单、自动补偿。课程项目几乎没人做，是"交易严谨性"的最好证明。

**⑨ 分库分表与读写分离**
- 订单表按用户 ID 取模分片（ShardingSphere）；
- 讲清分片键选择（为什么按用户不按订单 ID——旁路索引/基因法）；
- MySQL 主从读写分离 + 强制走主场景（刚写完的读）；
- 深挖点：分库分表后分布式 ID 怎么生成（雪花算法及时钟回拨处理）、跨分片分页查询怎么办。

**⑩ 并发编程显性化**
- CompletableFuture 并行聚合商品详情（库存 + 活动 + 评价 + 优惠券）；
- 线程池隔离：核心业务与非核心业务分开，参数结合压测调优；
- JUC 实际使用点：Semaphore 限并发、CountDownLatch、ThreadLocal 上下文传递（及线程池下 ThreadLocal 的坑）。

**⑪ 连接池与数据库调优**
- HikariCP/Druid 参数结合压测调整：maximumPoolSize 不是越大越好；
- 慢 SQL 治理：通过 SkyWalking/Arthas 定位，索引优化前后对比执行计划；
- 深挖点：连接池打满 → 线程阻塞 → 雪崩的传导链（这就是项目二注入的故障之一）。

**⑫ 全链路压测（必须出真实数据）**
- JMeter/wrk，记录优化前后曲线。简历写法示例：
  > 压测环境 4C8G×3 节点；初始 QPS 800 / P99 500ms；经热点缓存 + 异步下单 + 连接池与索引优化后 QPS 2500 / P99 180ms，全程零超卖。

**⑬ 可观测性（工程质量体现，也是项目二数据源）**
- 指标设计讲 RED 方法（Rate/Errors/Duration）+ USE（饱和度）；
- TraceId 贯穿微服务与 MQ（SkyWalking），日志统一打 TraceId/订单号（ELK）；
- 能讲一个真实故事："通过 SkyWalking 发现某 SQL 慢 → 加索引 → P99 从 X 降到 Y"。

### 1.3 简历话术（主条目，放最前）

### 2.3 可靠性机制（Java 自研，研究深度全保留）

**机制一：五级循环终止防护（防 Agent 失控空转）**

1. **硬性上限**：每任务 maxTurns（最大工具轮次）+ maxBudget（token/成本预算）+ 墙钟超时。工业界参照：Claude Code SDK 达到上限返回 `error_max_turns` / `error_max_budget_usd` 结果子类型，而不是静默死掉；
2. **重复调用检测（doom-loop detection）**：维护"同一工具 + 归一化参数"的连续重复计数（streak），随 streak 增长分级处置：observe（记录）→ steer（注入提示"你在重复"）→ escalate（换更强模型单轮救场）→ block（拒绝执行重复调用）→ stop（终止任务）。注意归一化参数，防止模型改个时间戳就绕过检测；
3. **无进展检测（stall detection）**：连续 N 轮没有新的信息增量（没有新工具结果类型、没有状态变化、没有结论产出）→ 暂停并上报；
4. **熔断器**：对某类恢复性操作（如压缩、重试）连续失败 3 次即熔断。参照 Claude Code 源码里的压缩熔断器（`MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3`），其源码注释引用生产数据：没有熔断器时曾出现单会话 3,000+ 次连续压缩失败、全局每天浪费约 25 万次 API 调用；
5. **优雅退出语义**：触顶后返回结构化结果（已完成的中间结论 + 未完成待办），会话状态存 Redis，支持续跑，而不是直接 abort。

**机制二：证据绑定 + 校验闭环（诊断不是 LLM 瞎编的）**

1. **声明-证据绑定（grounding）**：诊断报告的每个结论必须引用工具返回的具体证据（TraceId、日志行号、指标时间窗），格式强制为 `<claim evidence="toolCallId#offset">`。校验器程序化地回查每条 claim 的证据是否真实存在于工具输出中——**引不出证据的结论直接打回**；
2. **Maker-Checker 分离**：核心原则"绝不让 AI 自己验证自己已完成"。能用程序验证的用程序（证据回查、规则校验），不能的用独立 LLM judge + 评分 rubric，且 judge 用不同模型/不同提示词，避免同源偏见；
3. **置信度分层**：输出区分"确认事实（有工具证据）/ 合理推断（间接证据）/ 猜测"，不允许用同样自信的语气输出三种内容；
4. **幻觉反馈闭环**：用户纠正被结构化记录，沉淀到知识库，定期回归测试同类故障是否再犯。

**机制三：工具调用效率治理（80% 无效调用问题）**

1. **先量化定义**：重复调用 = 同工具同归一化参数被再次调用；无效调用 = 结果未被后续推理引用（用"该结果是否在后续消息中被提及/引用"近似判定）；
2. **预防**：工具结果预算（每个工具返回结果有大小上限，超了截断并给"完整结果已存至 ES/文件，可用区间读取工具获取"的指针）；工具清单延迟加载（工具多时不全量塞进提示词，先给检索工具）；探索性大任务下发给子代理（独立上下文，只回传摘要，防止撑爆主上下文）；
3. **治理**：机制一的重复检测天然拦截一部分；每轮结束计算"本轮信息增量"，连续零增量触发 steer/stop；
4. 这些都会变成评测里的**效率指标**，可以量化优化前后的差异——研究味道的来源。

**机制四：上下文管理——Java 复刻 Claude Code 四级压缩管线**

实现为可插拔的 `Compressor` 接口链（Chain of Responsibility），分级压缩：从快到慢、从无损到有损，前一层搞不定才升级：

1. **L1 工具结果预算（始终开启）**：每个工具返回结果设大小上限，超长截断 + 落 ES/文件 + 返回读取指针。**工具结果不是直接塞进上下文的**；
2. **L2 微压缩 MicroCompact（规则驱动，零 LLM 成本）**：把较早的工具结果原地替换为占位符（`[Old tool result content cleared]`），只保留最近 5 个可压缩工具的结果；触发时机刻意对齐 prompt cache 的 TTL（如 60 分钟无交互后），避免为主动清理破坏本来还能命中的缓存（缓存命中 token 计费约为原价十分之一）；
3. **L3 自动压缩 AutoCompact（LLM 摘要）**：阈值计算——200K 窗口先预留 20K 给摘要输出（该数值来自摘要长度 p99.99 统计），再减 13K 安全缓冲，即约 83.5%（167K）时触发。独立单轮 LLM 实例生成 9 段式结构化摘要（用户意图、技术概念、文件与代码、错误与修复、待办、当前工作、下一步等）；提示词采用"草稿纸模式"：先输出 `<analysis>` 推理草稿，再输出 `<summary>` 正式摘要，后处理删除 `<analysis>`；压缩完成后**自动重读最近访问的上下文**恢复工作现场；
4. **L4 阻塞限制 + 响应式兜底**：接近硬上限（仅留 3K 缓冲）直接拒绝发请求（比收到 API 的 413 错误再处理省一次调用）；真收到 `prompt_too_long` 错误时逐条丢弃最旧消息做最激进降级；压缩连续失败 3 次熔断。

补充机制：**部分压缩**（已有摘要时只压缩增量部分，省 token）与**会话记忆压缩**（后台持续增量记笔记，压缩时直接用笔记代替全量摘要）。

### 2.4 评测体系（研究属性核心，全保留）

**评测指标**（对齐业界基准方法学）：

| 维度 | 指标 | 方法学来源 |
|---|---|---|
| 效果 | 诊断任务成功率 pass@1；根因定位准确率（Top-1/Top-3 命中注入故障）；证据引用准确率 | τ-bench、SWE-bench % Resolved、RCAEval/OpenRCA |
| 稳定性 | pass^k：同一任务连跑 k 次全部成功的概率（衡量一致性，比单次成功率苛刻得多） | τ-bench |
| 工具效率 | 工具调用成功率、无效调用率、重复调用率、平均调用轮次 | 自定义 + BFCL 分类思想 |
| 成本 | 每任务 token 消耗（输入/输出分开）、折算成本、token/iteration | BFCL 的 Cost 列、SWE-bench 的 Avg.$ |
| 时延 | 每任务端到端耗时、每轮耗时分布 | BFCL Latency、SWE-bench wall-clock |
| 鲁棒性 | 多次重跑的方差（3~5 个种子） | SWE-bench 报告惯例 |

**关键创新点：故障注入产生 ground truth**。τ-bench 靠"对比数据库最终状态"判分，SWE-bench 靠"FAIL_TO_PASS 测试全过"判分——你的判分手段是：用 **ChaosBlade / Chaos Mesh** 在项目一系统里注入已知故障（杀节点、加网络延迟、灌满线程池、慢 SQL、打爆 Redis 连接、MQ 堆积），**根因是注入时记录的**，Agent 诊断结论与之比对即可自动判分，完全绕开"LLM 判断 LLM"的不可信环节。可对标阿里云 2026 年开源的 RCA Benchmark（业界首个面向 Agentic Ops 的根因分析基准体系）和学术界 RCAEval、OpenRCA。

**故障场景库**：CPU 飙高、慢 SQL、Redis 延迟、线程池打满、连接池耗尽、MQ 堆积、网络丢包、Pod kill、缓存击穿等 20+ 场景，每个场景记录注入参数与预期根因。

**实验设计（研究成色所在）**：
- **消融实验**：同一故障集上分别关闭 循环检测 / 四级压缩 / 证据绑定校验，观察成功率、重复率、token 消耗的变化——用数据回答"这些机制到底值多少"；
- **压力实验**：故意构造诱导死循环的任务（互相矛盾的线索）、超长工具输出（几十万行日志）、上下文爆长（50+ 轮排查），验证系统降级行为是否符合设计；
- **横向对比**：换不同底座模型跑同一故障集，输出类似 BFCL 的"准确率 × 成本 × 时延"对比表；
- **评测流水线工程化**：注入 → 采集 → 诊断 → 比对 → 报告，做成可重复执行的回归任务，接入 CI，体现"可测试、可度量"的工程能力。

### 3.2 面试攻防预案

每个项目先完成 [[../03-领域与长期/Java后端学习与投递路线图|路线图]] 的「项目话术三问」底稿（为什么做 / 架构怎么设计 / 踩过什么坑怎么解决，录音自讲验证），再按下面清单准备深挖追问。

**项目一必被深挖的问题**：
- 超卖怎么防？（Lua 原子性 → 为什么不用 DB 锁 → 消息没发出去怎么办）
- MQ 哪些环节丢消息？怎么保证不丢？（本地消息表/事务消息 → ACK → 刷盘/复制）
- 幂等怎么做？重复回调/重复消费/重复提交分别怎么处理？
- 缓存三大问题？缓存一致性方案权衡？
- 分库分表后分布式 ID、跨分片查询怎么办？
- 压测数据怎么来的？瓶颈在哪？怎么发现和优化的？
- Seata AT 的原理和脏写问题？为什么不用 TCC？

**项目二的话术策略**：
- 主线讲：系统架构、异步化设计、虚拟线程并发模型、工具注册与调用机制、证据链存储与验证、评测流水线、混沌工程；
- 被追问机制时（这是你的主场）：按"工程问题 → 机制 → 数据"讲——"压缩阈值 83.5% 怎么定的"（20K 摘要预留来自 p99.99 统计 + 13K 缓冲）、"pass^k 和 pass@1 差别说明什么"（τ-bench 结论：模型重复执行同一任务的稳定性远差于单次成功率）、"微压缩为什么对齐 prompt cache TTL"（缓存命中 token 约 1/10 价格，主动清理过早反而亏钱）；
- "为什么用 Java 不用 Python 写 Agent？"→ 与主系统同栈复用基础设施；从原理自研而非调库，理解更深；虚拟线程天然契合 I/O 密集的 Agent 会话；类型安全与工程化测试体系；
- 研究产物的使用：逆向报告和消融实验数据是"技术热情与深度"的证据，面试时主动提一句"我把这个机制的工业界实现（Claude Code）逆向分析过，写了份报告"，然后等面试官要。

**通用八股照常准备**：分布式一致性、缓存穿透/雪崩、消息可靠性、JVM 调优、索引与执行计划、K8s 原理。项目再强也替代不了八股和算法。

### 3.3 项目吃透方法与必备产出物（三层递进）

项目一、项目二均按三层递进吃透；AI 拆解的每个结论必须在代码里找到证据才可采信（"AI 说这里用了 Redis 缓存"→ 去找到那几行代码）。

| 层 | 做什么 | 产出 |
|---|---|---|
| 架构层 | 请求从哪进（Controller）、经过哪几层（Service/Mapper）、数据存哪、怎么部署 | 一张架构图 |
| 模块层 | 逐业务模块过：登录与鉴权（JWT/Session）、CRUD 完整链路、每个模块的边界情况 | 每模块一节笔记（并入开发文档） |
| 事件层 | 挑 3–5 个核心业务事件（如"用户下单"全流程），从接口到数据库完整追踪事务、异常处理、边界情况 | 每事件一段链路追踪记录 |

三层总产出：**一份开发文档 + 一张架构图**，作为 3.2 三问底稿与深挖回答的弹药库，也是项目验收"可解释"的具体形态；压测数据和可观测性结论直接引用进文档。苍穹外卖与黑马点评阶段只做轻量版：跟练结束时各画一张架构图 + 写一页模块笔记，不做事件层。
