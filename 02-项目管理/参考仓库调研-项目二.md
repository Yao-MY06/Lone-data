**gemini-cli 的 LoopDetectionService（本次已读源码，最具参考价值）**，三级检测：
1. 工具调用级：每个工具调用（名称+JSON 参数）SHA-256 哈希，检测周期长度 1–5 且重复 ≥5 次（`TOOL_CALL_LOOP_THRESHOLD=5`）的模式—— identical 调用与 A→B→A→B 固定动作循环都可捕获；
2. 内容复读级：50 字符滑窗 chunk 出现 10 次且平均间距 ≤5 倍 chunk 大小即判定，代码块内豁免，遇表格/列表/标题重置；
3. LLM 判定级：单提示 30 轮后启动，自适应间隔 5–15 轮，取最近 20 轮交诊断提示词，置信度 ≥0.9 且经第二个模型复核后确认。支持按会话禁用、遥测上报。
> 这三级结构可直接映射为自研"五级终止防护"中 doom-loop 检测的分级处置梯度。

**OpenHands Condenser**（软件已拆分到 SDK 仓，Python）：`llm_summarizing_condenser.py`（LLM 摘要）、`pipeline_condenser.py`（多级串联，天然对应"管线"抽象）、`no_op_condenser.py`（空实现基线）、`prompts/summarizing_prompt.j2`（摘要提示词模板）、`README.md` 与 `examples/01_standalone_sdk/14_context_condenser.py`。
> PipelineCondenser 的接口抽象（Condenser 协议 + 管道组合）是四级压缩管线 Java 接口设计的最佳参照。

**aider ChatSummary**：递归二分摘要——头部分（超出 1024 token 预算的较旧消息）送摘要、尾部保留原文；头部裁剪时预留 512 token 安全缓冲；剩余 ≤4 条或递归深度 >3 时退化为全量摘要；多模型依次 fallback。是"微压缩+摘要+兜底"最简可用范式。

**怎么用**：把这 7 家做成"压缩机制 × 循环防护"对比矩阵写进逆向报告/设计文档，自研机制的差异点（分级处置、grounding 回查）就有据可依。

### B3. RCA / AIOps 基准与系统

**1. phamquiluan/RCAEval（244★，活跃，FSE'26/WWW'25/ASE'24）**
- 数据：9 个数据集、**735 个真实故障案例**（RE1/RE2/RE3 × Online Boutique/Sock Shop/Train Ticket），11 种故障类型；RE1 仅 metrics（125 例/集），RE2 含 metrics+logs+traces（90 例/集），RE3 为代码级多源故障（30 例/集）；HuggingFace 分发（Parquet，3.4GB）。
- 判分：主指标 **Avg@5**（根因 top-5 命中），另有 Retrieval@K/Rerank@1 分解与 Chance@5/Lift@5 随机基线报告。
- 基线：17+ 种（BARO、RCD、CIRCA、MicroCause、EasyRCA、TraceRCA、MicroRank、TORAI 等）。
- 复用度：**最高**——数据、判分脚本、基线全部可直接跑；可把自研 Agent 接进其评测协议。

**2. microsoft/OpenRCA（439★，活跃，ICLR'25）**
- 数据：Telecom/Bank/Market 三个系统，遥测含 KPI 时序、trace 图、日志；数据经 Google Drive 分发；附 RCA-agent 基线（`run_agent_standard`）。
- 判分：根因定位答案与 ground truth 匹配（论文口径；精确案例数本次未在 README 核实，建议引用论文）。
- 复用度：高——故障场景与判分逻辑可直接复用，且其基线 agent 是自研引擎的现成对照组。

**3. itbench-hub/ITBench（512★，活跃，IBM Research，ICML 2025）**
- 内容：K8s 环境的 IT 自动化基准，SRE/CISO/FinOps 三线；README 口径 6 个 SRE 场景 21 种机制（2025-06 数据，后续有扩展路线）；2026-05 ITBench-AA 公告称 **59 个 SRE 任务上所有前沿模型得分均低于 50%**（可作为"问题难度"论据）。
- 判分：push-button 工作流 + 可解释指标 + 托管 leaderboard（环境由 IBM 托管，本地跑 agent、提交输出判分）。参考 SRE Agent 基于 CrewAI（独立仓 itbench-sre-agent，已归档迁入新仓）。
- 复用度：中——场景编排思路（K8s+故障声明）值得借鉴；直接复用需接其托管流程，自主评测流水线不便。

**4. RCA100 / AgenticOpsEval（即规划文档所指"阿里云 RCA Benchmark"的最可能对应物）**
- 论文：arXiv:2606.29193《A Multi-Dataset Benchmark for Evaluating LLM Agents in Microservice Failure Diagnosis》（2026-06-28，cs.SE）。
- 数据：RCA100 + AIOps2025 两个新数据集，合计 **500+ 专家标注故障案例**；系统为 HipsterShop 与 OpenTelemetry Demo Store；故障覆盖资源、网络、运行时、中间件/数据库、应用逻辑五类，带细粒度因果证据；经 6000+ 队伍的大型竞赛验证。托管于 **aiops.cn 的 GitLab（aiops-live-benchmark/agenticopseval）**，RCA100 许可证 CC BY-NC-SA 4.0。
- 判分：三维——**Localization（定位）、Identification（定性）、Reason（推理链是否 grounded 于证据）**。
- 重要提示：Reason 维度与本项目"声明-证据绑定 grounding"天然对齐，是选题合理性的强论据。作者列表含 Dan Pei、Changhua Pei、Shenglin Zhang（清华/南开 AIOps 团队）与 Xidao Wen 等；**是否官方"阿里云"归属未能 100% 核实**，报告中建议表述为"阿里系 AIOps 竞赛生态的 RCA100 数据集（AgenticOpsEval）"并附 arXiv 出处。

**5. GreptimeTeam/agent-rca-bench（2★，活跃，Greptime 赞助）**
- 内容：成对比较"可观测接口"对 LLM RCA 的影响（split_pillars 原生 Prom/Loki/Tempo API vs raw SQL/PromQL vs semantic_graph 语义图谱），控制模型/事故/提示词/预算不变；三层任务（Discovery / Graph retrieval / End-to-end RCA）；数据为 10 个 OpenRCA2 + 4 个 RCA100 事故，192 微基准格 + 504 端到端格；判分规则固化在 SCORING.md（行数、输入 token、工具调用数等效率指标 + 诊断正确性，Holm 校正）。
- 复用度：设计参考——"冻结协议、成对比较、先注册指标再跑实验"的方法学可直接搬进自研评测流水线。
- 另注：OpenRCA2 数据集托管于 HuggingFace `anon-ops/ops-lite`（许可证口径有冲突，引用前自查）。

3. **张汉东《驾驭工程》**（1.5k★）——第 3 章 Agent Loop、上下文管理与缓存章节深读；
4. **paicoding.com/claude-code-compaction**——四级压缩逐机制细节与阈值（83.5%/167K/3 次熔断）；
5. **xiufengsun/claude-code-prompt**——系统/工具提示词章节素材（引用前与源码交叉验证版本）；
6. **hahahuahai/claude-code-source**——按图索骥找全 8 个社区源码仓（ghuntley 991★ 仓含 cleanroom 方法论与合规声明范本；源码出自 npm 包 source maps 这一事实必须写进报告的合规声明）；
7. 对照组：**gemini-cli LoopDetectionService**（源码已核实）+ **OpenHands Condenser** + **aider history.py**——证明"自研五级防护/四级压缩"不是复述 CC，而是有横向对比的设计。

### ② Java 自研 Agent 的"借鉴 vs 必须自研"边界

**可以放心借鉴（读机制、抄参数、不抄代码）：**
- doom-loop 检测：gemini-cli 的三级检测（哈希重复 5 次、内容复读、LLM 判定 0.9 置信度+复核）作为分级阈值起点；loopguard 的五启发式清单作为维度补全；
- 压缩管线：OpenHands 的 Condenser 接口抽象（协议 + PipelineCondenser 串联）、aider 的递归二分摘要与 512 token 安全缓冲、paicoding 文中的 CC 四级阈值；
- 工具系统：CC 的并行读/串行写、大结果落盘策略（Windy 仓有归纳）；
- 评测协议：RCAEval/OpenRCA 的判分脚本直接复用，τ-bench 的 pass^k 定义直接引用，Greptime 的"冻结协议+先注册指标"方法学直接照搬流程。

**必须自研（项目的工程与叙事核心）：**
- Agent 执行引擎主体（规划→工具→观察→结论循环的 Java 实现）；
- 五级循环终止防护的分级处置状态机（检测→降级→降级再试→熔断→终止的转移逻辑，现有项目均无此分级处置）；
- 四级上下文压缩管线（工具结果预算/微压缩/LLM 摘要/阻塞兜底的 Java 实现与预算分配策略）；
- 声明-证据绑定 grounding（结论强制携带证据引用 + 程序化回查）——**开源界无现成实现，是最强原创点**，且 RCA100 的 Reason 评分维度为其提供外部判分依据；
- 混沌注入 → 数据采集 → 判分的自动化评测流水线（chaosblade-box/Chaos Mesh API 只是触发器，流水线本身自研）。

**底座红线：** Spring AI 只用 ChatClient/模型适配层；不引入 langgraph4j、spring-ai-alibaba graph、agents-flex 的 agent 编排能力，否则"自研引擎"叙事崩塌。
