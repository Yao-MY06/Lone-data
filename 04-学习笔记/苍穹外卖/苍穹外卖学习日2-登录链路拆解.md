## 一、调用链全景

```
前端 POST /admin/employee/login {"username":"admin","password":"123456"}
  ↓
① EmployeeController.login()          @RequestBody 转 EmployeeLoginDTO，调 service，签发 JWT
  ↓
② EmployeeServiceImpl.login()         业务规则：查→判空→比密码→判状态
  ↓
③ EmployeeMapper.getByUsername()      @Select 注解，MyBatis 动态生成实现
  ↓
④ MySQL sky_take_out.employee
  ↓
返回 Result<EmployeeLoginVO>{id, userName, name, token}
```

**这条链是整个项目的模板** —— 后面菜品、订单、分类所有接口都是这个形状。

## 二、逐层要点（"抄明白"的核心）

### ① DTO / VO / Entity 三者的区别

| 类型 | 对应什么 | 例子 |
| --- | --- | --- |
| **Entity** | 数据库表 | `Employee`：12 个字段，含 idNumber、createTime 等 |
| **DTO** | 进来的参数 | `EmployeeLoginDTO`：只有 username、password |
| **VO** | 出去的响应 | `EmployeeLoginVO`：id、userName、name、token |

**为什么不用 Entity 直接接收？** 登录只需要 2 个字段，用 Entity 会逼前端传无关字段（还要传 idNumber 这种敏感信息）。DTO 的作用是**收窄入参**。

**为什么 VO 里有 `token` 字段而表里没有？** 因为 token 是登录时临时生成的，不落库。VO 对应"界面需要什么"，不是"表里有什么"。

### ② Controller 只做三件事

```java
@RestController                  // = @Controller + @ResponseBody
@RequestMapping("/admin/employee")   // 类级前缀
public class EmployeeController {
    @PostMapping("/login")       // 方法级后缀 → 拼成 /admin/employee/login
    public Result<EmployeeLoginVO> login(@RequestBody EmployeeLoginDTO dto)
}
```

- 接请求、转交 service、包响应 —— **不写业务逻辑**（业务要能被复用和测试）
- **URL 前缀区分端**：`/admin/**` 管理端，`/user/**` 用户端。这个前缀直接决定拦截器管不管

### ③ Service 是业务规则的唯一位置

```java
Employee employee = employeeMapper.getByUsername(username);  // 先查一次
if (employee == null)  throw new AccountNotFoundException(...);   // ① 不存在
if (!password.equals(employee.getPassword())) throw new PasswordErrorException(...);  // ② 密码错
if (employee.getStatus() == StatusConstant.DISABLE) throw new AccountLockedException(...);  // ③ 被禁用
```

**三个设计点：**
1. **查一次，判三次** —— 不要在内存里判，更不要查三次库
2. **顺序不能乱** —— 先比密码就会 NPE（employee 可能是 null）
3. **抛异常而非返回 null** —— 由 `GlobalExceptionHandler` 统一转成 `Result.error(msg)`

**源码里的 `// TODO 后期需要进行md5加密`** 是讲义 day02 预留的改造点。

### ④ Mapper 的一行注解

```java
@Mapper
public interface EmployeeMapper {
    @Select("select * from employee where username = #{username}")
    Employee getByUsername(String username);
}
```

- 只写接口，**MyBatis 启动时动态生成实现类**
- `#{}` = 预编译占位符（PreparedStatement 的 `?`），**防 SQL 注入**
- `${}` = 字符串拼接，**有注入风险，永远不要用**

### ⑤ JWT 的真实结构（已实测解码）

登录返回的 token：
```
eyJhbGciOiJIUzI1NiJ9.eyJlbXBJZCI6MSwiZXhwIjoxNzkxNDUxMTAzfQ.TNkaysG2ah7V_AV4JaQBY2DrhZJua7y4j1l3QS-pGyA
```

实测 Base64 解码结果：

| 段 | 内容 |
| --- | --- |
| Header | `{"alg":"HS256"}` |
| **Payload** | **`{"empId":1,"exp":1791451103}`** ← 明文可读！ |
| Signature | `TNkaysG2...`（不可逆，只能验签） |

**核心认知：Payload 是 Base64 编码，不是加密。** 任何人拿到 token 都能解出 empId。安全性来自第三段签名 —— 改动 payload 会导致签名不匹配，服务端验签失败。

> **推论：永远不要把密码、身份证号等敏感信息放进 JWT。**

### ⑥ 拦截器如何工作

```java
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    if (!(handler instanceof HandlerMethod)) return true;   // 静态资源直接放行
    String token = request.getHeader(jwtProperties.getAdminTokenName());  // 从请求头取
    try {
        Claims claims = JwtUtil.parseJWT(jwtProperties.getAdminSecretKey(), token);
        Long empId = Long.valueOf(claims.get(JwtClaimsConstant.EMP_ID).toString());
        return true;        // 通过，放行
    } catch (Exception ex) {
        response.setStatus(401);
        return false;       // 不通过，拦下
    }
}
```

**注册方式（WebMvcConfiguration）——这里有逻辑闭环：**
```java
registry.addInterceptor(jwtTokenAdminInterceptor)
        .addPathPatterns("/admin/**")                    // 拦所有管理端
        .excludePathPatterns("/admin/employee/login");   // 但必须放行登录本身
```

登录接口若要 token 才能访问，就永远登不进去了 —— 所以必须 exclude。

## 四、MD5 密码加密改造（已完成并验证）

### 4.1 改造背景

**问题**：数据库里 `admin` 的密码是明文 `123456`，任何人拖库就能看到全部密码。

### 4.2 改造内容（两步，缺一不可）

**第 1 步：改 Java 代码** —— `sky-server/.../service/impl/EmployeeServiceImpl.java`

`DigestUtils` 是 **Spring 自带的**（在 `spring-core` 里），**不需要加任何 Maven 依赖**，初始工程已有 import。

```java
// 改造前
// TODO 后期需要进行md5加密，然后再进行比对
if (!password.equals(employee.getPassword())) {
    throw new PasswordErrorException(MessageConstant.PASSWORD_ERROR);
}

// 改造后
//密码比对：把用户输入的明文密码进行 MD5 加密后，再与数据库中的密文比对
password = DigestUtils.md5DigestAsHex(password.getBytes());
if (!password.equals(employee.getPassword())) {
    throw new PasswordErrorException(MessageConstant.PASSWORD_ERROR);
}
```

**第 2 步：修正数据库存量数据** —— 不做这步会登不进去

```sql
USE sky_take_out;
UPDATE employee SET password = 'e10adc3949ba59abbe56e057f20f883e' WHERE username = 'admin';
```

执行前后对比：`123456`（6 位明文）→ `e10adc3949ba59abbe56e057f20f883e`（32 位摘要）。改了代码不改数据 = 明码比摘要 = 永远不等。

### 4.3 实测验证（2026-10-08）

| 实验 | 输入 | 结果 | 说明 |
| --- | --- | --- | --- |
| 1 | 密码 `123456` | ✅ `{"code":1,...,"token":"eyJ..."}` | 明文能正常登录 |
| 2 | 密码 `wrong` | `{"code":0,"msg":"密码错误"}` | 校验逻辑正常 |
| 3 | 密码填 `e10adc3949ba59abbe56e057f20f883e` | `{"code":0,"msg":"密码错误"}` | **反证改造生效：服务端会再算一次 MD5** |

实验 3 是关键 —— 传现成的 MD5 值反而登不进，证明服务端确实在做"输入 → MD5 → 比对"。

### 4.4 必须理解的三个原理

**① 为什么用「摘要」而不是「加密」？**

服务器**不需要知道密码原文**，只需要判断"输入的和库里的是否同一个"。加密（AES 等）是可逆的，密钥泄露 = 全部密码泄露；摘要（MD5）不可逆，只能比对。

> 加密 = 把信锁进保险箱（有钥匙能取回原文）
> 摘要 = 给信按指纹（只能比对，取不回原文）

**② 为什么不能直接 `password.equals(employee.getPassword())`？**

前端传明文，库里存摘要，类型都不是一个东西，直接比永远不相等。必须先算摘要再比。

**③ MD5 无盐的风险（这里推导出的完整攻击链）**

```
MD5 无盐 → 相同密码产生相同摘要 → 彩虹表可反查明文
        → 攻击者知道"密码是什么"
        → 配合已知的用户名 → 登录成功
```

**修正一个常见误解**：MD5 相同**不会**让人登到别人账号。因为登录是"**先按用户名查，再比这一行的密码**"，不是"拿密码去全表匹配"。泄露的是"密码本身"，不是"登录权限"。

**加盐的价值**：让每个用户的摘要都不同（`md5(密码+盐)`），把"破一次、全表通吃"变成"必须逐个用户破解"。

### 4.5 MD5 的局限（面试加分项）

MD5 已被证明不安全：可碰撞、可彩虹表反查必中弱密码。生产环境应该用 **BCrypt / Argon2**（自带随机盐 + 可调计算强度）。

**现成的便利条件**：表设计 `password varchar(64)` 留了余量 —— MD5 是 32 位，BCrypt 是 60 位，**升级不需要改表结构**。

**面试应答模板**：
> "MD5 无盐的话，相同密码产生相同摘要，彩虹表可以直接反查弱密码。攻击者一旦知道明文密码，配合用户名就能登录。所以生产环境要用 BCrypt 这类加盐哈希，让每个用户的摘要都不同，把'破一次全表通吃'变成'必须逐个破解'。"

### 4.6 本次踩的坑

1. **改完代码必须重启应用** —— Spring Boot 启动时把 class 加载进内存，不重启跑的还是旧逻辑。会出现"明明改对了却登不进去"的假象。
2. **排查意外结果时，先确认"测的是不是我以为的那个程序"** —— 本次验证时 8080 上跑的还是旧进程（端口被占），导致误判为改造失败。`netstat -ano | grep :8080` 能确认。
3. **`java -jar` 用绝对路径** —— 相对路径 `../../` 会报 `Unable to access jarfile`。

### 5.3 四个必须理解的机制

**① REST 风格 —— URL 表资源，HTTP 方法表动作**

```java
@PostMapping          // 新增        → POST   /admin/category
@GetMapping("/page")  // 分页查询    → GET    /admin/category/page
@PutMapping           // 修改        → PUT    /admin/category
@DeleteMapping        // 删除        → DELETE /admin/category
```

核心思想：**URL 不该出现动词**。`/getUserById` 是坏设计，`GET /users/1` 才是好设计。项目里两种风格混用（登录用 `/login` 动词式是为了语义直白）。

**② BaseContext —— 跨层传递当前用户（ThreadLocal）**

```
拦截器解析 token → empId → BaseContext.setCurrentId(empId)
                              ↓（ThreadLocal 中转）
Service：BaseContext.getCurrentId() → 填入 create_user
```

解决什么问题：`save()` 只接收 DTO，没有 empId 参数。传统做法要层层传参，用 ThreadLocal 提供"隐形通道"。

**为什么不会串数据**：每个 HTTP 请求由独立线程处理，ThreadLocal 是线程私有存储。请求结束线程回收，数据自然消失。

**③ PageHelper —— 一行代码分页**

```java
PageHelper.startPage(dto.getPage(), dto.getPageSize());   // 声明分页
Page<Category> page = categoryMapper.pageQuery(dto);      // 下一条 SQL 自动加 LIMIT
return new PageResult(page.getTotal(), page.getResult()); // 取总数 + 列表
```

原理：`startPage` 把分页参数存进 ThreadLocal，在下一条 SQL 执行时拦截并拼上 LIMIT，同时额外查一次总数。

**坑**：`startPage` 只对**紧挨着的下一条 SQL** 生效，中间插别的查询会导致分页错位。

**注解 vs XML 的分工**：简单单表查询用 `@Select` 注解（如 `getByUsername`）；动态条件（`<if>` 拼接）写 XML。

**④ 删除前的关联校验 —— 面试常问**

```java
Integer count = dishMapper.countByCategoryId(id);      // 先查菜品引用
if (count > 0) throw new DeletionNotAllowedException(...);
count = setmealMapper.countByCategoryId(id);           // 再查套餐引用
if (count > 0) throw new DeletionNotAllowedException(...);
categoryMapper.deleteById(id);                         // 都通过才删
```

**为什么不用数据库外键？** 苍穹故意不建物理外键（都是逻辑外键），原因：① 外键检查有性能开销；② 分库分表后跨库外键无法维护。**代价是一致性必须由应用层保证。**

**面试标准答法**：
> "我们项目用的是逻辑外键，没有物理外键约束。一致性由应用层保证，比如删除分类前会先校验是否关联了菜品或套餐。代价是失去了数据库级强约束，但换来了分库分表的能力和更好的性能。"

**⑤ 附带：BeanUtils.copyProperties**

```java
BeanUtils.copyProperties(categoryDTO, category);   // 按属性名自动拷同名同类型字段
category.setStatus(StatusConstant.DISABLE);        // DTO 里没有的字段手动补
category.setCreateUser(BaseContext.getCurrentId());
```

注意：只拷贝名字和类型都相同的字段；是**浅拷贝**（对象/集合属性拷的是引用）。
