## 一、分层限流防刷（网关限流 / Sentinel 熔断 / 秒杀 URL 动态化 / 验证码）

### 1. gz-yami/mall4cloud — https://github.com/gz-yami/mall4cloud
- Star 约 6.2k；2026-10-19 仍在提交；Spring Boot 4 + Spring Cloud（README 证实 Nacos、Seata、RocketMQ、Canal、Leaf、ES；未用 Sentinel/SkyWalking/ShardingSphere）。
- 对应技术点：1、2、4、6、9（Leaf 发号）。
- 实现质量：`mall4cloud-gateway`（8000 端口唯一入口）+ `mall4cloud-common-*` 公共模块划分清晰，是「网关层怎么组织、公共模块怎么拆」的最好活样本。README 未提 Sentinel，网关限流需自己补。
- 怎么用最值：精读 gateway 模块的路由/过滤器组织方式与 `mall4cloud-common-rocketmq`、`mall4cloud-common-cache` 的封装方式；不要读业务 CRUD。

## 二、缓存体系（Cache Aside / 布隆过滤器 / 逻辑过期 / 随机过期 / 多级缓存 / 延迟双删 vs Canal）

### 1. alibaba/jetcache — https://github.com/alibaba/jetcache
- Star 约 5.6k；2026-08-22 有提交。
- 对应技术点：2（`@Cached` 注解 + Caffeine(local)+Redis(remote) 声明式两级缓存是官方一等公民）。
- 怎么用最值：精读其 two-level cache 的配置方式与 `@CacheRefresh` 刷新机制；你自己的项目可以「用 JetCache 或仿它手写一个两级缓存抽象」，面试讲设计取舍。
- 定级：模块级参考。

### 2. redisson/redisson — https://github.com/redisson/redisson
- Star 约 24.4k；2026-10-16 活跃。
- 对应技术点：2（RBloomFilter 布隆过滤器）、3（分布式锁）、7（RDelayedQueue）。
- 怎么用最值：布隆过滤器直接用 RBloomFilter，不必另找仓库；顺带看其源码里 Lua 脚本写法，是你写库存 Lua 的语法范本。
- 定级：生产级参考（组件）。

### 3. alibaba/canal — https://github.com/alibaba/canal
- Star 约 29.7k；2026-07-30 活跃。
- 对应技术点：2（binlog 订阅 → 刷缓存/ES）。
- 怎么用最值：跑通官方 `canal.example`（client 订阅示例）即可，面试重点是「为什么选 Canal 而不是延迟双删」的论证，而不是源码。
- 定级：生产级参考（组件）。

### 4. gz-yami/mall4cloud（复用）
- README 证实其技术栈含 **Canal**，且仓库有 `mall4cloud-common-cache` 模块——这是活跃商城项目里少见的「Canal 缓存同步」落地样本。
- 怎么用最值：精读 mall4cloud 里 Canal 客户端的消费与缓存失效代码（对应表：商品/分类缓存）。
- 定级：模块级参考。

### 5. ben-manes/caffeine — https://github.com/ben-manes/caffeine
- Star 约 17.9k；2026-10-19 当日活跃。
- 对应技术点：2（本地缓存选型基准）。怎么用：只看 wiki 的命中率 benchmark 与驱逐策略（Window TinyLFU），为「为什么本地缓存选 Caffeine 而非 Guava」提供弹药。
- 定级：生产级参考（组件）。

### 6. macrozheng/mall-learning — https://github.com/macrozheng/mall-learning
- Star 约 13.4k；最近提交日期未能精确核实。
- 对应技术点：2、11（部署文档）。怎么用：只查「Redis 缓存使用」「ELK」等单篇文档，当 cheatsheet，不进简历。
- 定级：教学玩具慎学（文档可用）。

> 「延迟双删」说明：经搜索，GitHub 上没有有分量的、以延迟双删为主题的独立仓库，它本质上是 20 行代码的模式而非框架。建议在自己的项目里用 RocketMQ 延迟消息实现一次「可配置延迟的二次删除」，并与 Canal 方案做 A/B 论证——这本身就是差异化亮点。逻辑过期/随机过期同理，属于自实现模式，可对照 JetCache 的 refresh 设计。

**本节结论**：主参考 Jetcache（多级缓存落地）+ mall4cloud 的 Canal 用法；辅参考 Redisson 的布隆过滤器与 mall-learning 的缓存文档。延迟双删/逻辑过期/随机过期自实现。

## 三、库存扣减（Redis Lua 原子扣减 / 热点 Key 拆分 / 子 Key 回收 / 分布式锁对比）

### 1. weiraneve/seckillcloud — https://github.com/weiraneve/seckillcloud
- README 证实：Redis 库存预热 + **Lua 脚本原子预减库存防超卖**；并对比过 synchronized 与 Redisson 锁后选择 Lua（有明确的选型记录）。
- 怎么用最值：精读其 Lua 脚本与预减/回补逻辑，是「Lua 扣减」最直接的近期代码样本（2026-09 仍在更新）。
- 定级：模块级参考。

### 2. redisson/redisson（锁的一方）
- 看门狗自动续期、可重入锁、MultiLock/RedLock 均有官方实现与文档。
- 对应技术点：3（Redisson 看门狗 vs ZK 锁的对比论证素材）。
- 定级：生产级参考（组件）。

### 3. baomidou/lock4j — https://github.com/baomidou/lock4j
- Star 约 403；2025-09-10 有提交。
- 对应技术点：3（注解式分布式锁，同时支持 RedisTemplate/Redisson/ZK 三种实现——正好做锁对比实验的脚手架）。
- 怎么用最值：借它的抽象接口设计，把「锁可替换」做成你项目里的一个 SPI 点。
- 定级：模块级参考。

### 4. JD hotkey（京东热点 key 探测）— Gitee: https://gitee.com/jd-opensource/hotkey（fork，上游为 jd-platform-opensource/hotkey，约 1.4k fork）
- GitHub 原仓（jd-opensource/hotkey）已 404，未能核实；Gitee 镜像内容停留在 2020 年前后（README 提及 2020 年 618/双11）。
- 对应技术点：3（热点 key 毫秒级探测 + 推送到集群内存——「热点库存拆分」的工业界前序方案）。
- 怎么用最值：读设计与 worker/client 通信思路即可；你项目里的「热点 Key 拆分到 Cluster 多节点 + 子 Key 回收」基本需要自实现，hotkey 负责回答「怎么发现热点」。
- 定级：模块级参考（设计层面）。

> 「热点库存拆分+子 Key 回收」说明：经多轮搜索（热点库存/库存拆分/hotkey 等关键词），公开仓库中**没有**成体系的真实代码实现，只有零散学习 fork（如 OneSheep123/hotkey，0★）。这恰是差异化机会：自实现「按 Cluster 槽位拆 N 个子 Key + Lua 聚合扣减 + 订单取消时按子 Key 归还」即可超越绝大多数简历。

**本节结论**：主参考 weiraneve/seckillcloud（Lua 扣减）+ Redisson 官方文档（锁对比）；辅参考 JD-hotkey（热点探测设计）。热点拆分与子 Key 回收建议自实现。

## 四、MQ 削峰与可靠消息（本地消息表 vs 事务消息 / 消费幂等 / 顺序消息 / 积压预案）

### 1. apache/rocketmq — https://github.com/apache/rocketmq（22.6k，2026-10 活跃）
### 2. apache/rocketmq-spring — https://github.com/apache/rocketmq-spring（2.3k，2026-07-24）
- 对应技术点：4、7。
- 怎么用最值：`rocketmq-spring-boot-samples` 里有事务消息（transaction）、顺序消息（orderly）、延迟消息（delay）三类可直接跑的 Spring 示例——这是你落地 4/6/7 三个技术点的最短路径。顺序消息按订单 ID 哈希选队列就是官方示例的标准用法。
- 定级：生产级参考。

### 3. dromara/myth — https://github.com/dromara/myth
- Star 约 1.5k；最近提交精确日期未能核实（dromara 早期项目，近年更新慢）。
- 对应技术点：4、6（本地消息表=可靠消息最终一致性分布式事务，支持 RabbitMQ/Kafka/RocketMQ，本地消息存储支持 MySQL/Redis/MongoDB 等）。
- 怎么用最值：精读其消息状态机（待确认→已发送→已完成）与定时补偿任务设计，然后在自己的项目里**手写一个精简版本地消息表**（面试时「我读过 myth 但选择自实现，原因是……」比「我用了 myth」加分得多）。
- 定级：模块级参考。

### 4. paascloud/paascloud-master — https://github.com/paascloud/paascloud-master
- Star 约 9.9k；2023-10 后基本停更；Spring Cloud Edgware 时代的老栈（topics 含 rocketmq）。
- 对应技术点：4（它是国内最早一批把「可靠消息服务（本地消息表）」做成独立微服务的开源商城）。
- 怎么用最值：只看其可靠消息服务中心的表设计与重试/死信流转，不要看其他（技术栈过老）。
- 定级：模块级参考。

### 5. dromara/hmily — https://github.com/dromara/hmily（4.2k，2024-07 后无提交）
### 6. codingapi/tx-lcn — https://github.com/codingapi/tx-lcn（4.2k，2023-09 停更）
- 对应技术点：4、6 的**对比素材**：TCC（hmily）与 LCN 模式均已停更，正好支撑面试中「为什么最终业界收敛到 Seata AT + 本地消息表/事务消息」的论述。
- 定级：模块级参考（只读设计文档）。

**本节结论**：主参考 rocketmq-spring 官方 samples（事务/顺序/延迟三类）+ myth（本地消息表设计）；辅参考 paascloud（可靠消息业务化样本）。消费幂等（唯一键去重表）与消息积压预案未见有分量开源实现，建议自实现并把积压预案写进项目文档（扩容消费者、降级批量处理、死信监控）。

## 七、超时关单与库存/券回补（延迟消息 vs DelayedQueue vs 定时轮询）

### 1. macrozheng/mall — https://github.com/macrozheng/mall
- Star 约 84.9k；2026-09-15 活跃；master 已升 Spring Boot 3.5 + JDK 17。
- 对应技术点：7（本报告直接核实了源码文件 `mall-portal/.../OmsPortalOrderServiceImpl.java`）：
  - 下单时 `sendDelayMessageCancelOrder(orderId)`，延迟时长取自 `orderSetting.getNormalOrderOvertime()`，经 `CancelOrderSender.sendMessage(orderId, delayTimes)` 发 MQ 延迟消息；
  - 消费端 `cancelOrder` 只取消未支付订单，并**释放锁定库存（releaseSkuStockLock）+ 重置优惠券状态 + 退回积分**——「关单回补三件套」的完整代码；
  - 另有 `cancelTimeOutOrder()` 批量扫描超时订单——MQ 延迟之外的**定时轮询兜底**，两种方案在同一文件里共存，正好做对比论证。
- 怎么用最值：精读这一个类的下单-延迟关单-回补链路（约几百行），是全开源界最干净的「超时关单」样本。延迟消息底层是 RabbitMQ 插件还是 TTL+DLX 在 `CancelOrderSender` 中，需要再往下追一层。
- 定级：模块级参考（注意：mall 整体叙事已烂大街，见文末清单）。

### 2. redisson/redisson（RDelayedQueue）
- 对应技术点：7 的方案 B（Redisson DelayedQueue）。官方 wiki 有完整用法，直接引用即可。
- 定级：生产级参考（组件）。

### 3. apache/rocketmq（5.x 任意时间延迟消息）
- 对应技术点：7 的方案 A。RocketMQ 5.x 支持秒级任意延迟（4.x 只有 18 个固定级别），这是面试加分点。
- 定级：生产级参考。

### 4. PowerJob/PowerJob — https://github.com/PowerJob/PowerJob（7.8k，2026-10-01 活跃）
### 5. xuxueli/xxl-job — https://github.com/xuxueli/xxl-job（30.6k，2026-10-09 活跃）
- 对应技术点：7 的方案 C（分布式定时轮询关单 + 第八节对账定时任务）。
- 怎么用最值：二选一接入做兜底任务即可；xxl-job 用户基数大、PowerJob 功能更强（MapReduce 分布式计算适合批量对账）。
- 定级：生产级参考（组件）。

**本节结论**：主参考 mall 的 OmsPortalOrderServiceImpl（延迟消息+定时兜底+回补三件套）；辅参考 Redisson DelayedQueue 与 RocketMQ 5.x 任意延迟做方案对比。面试标准答案：「延迟消息为主 + 定时扫描兜底 + 关单动作幂等」。

## 八、对账系统（三方对账 / 差错处理）—— 最稀缺，重点调研结论

### 1. roncoo/roncoo-pay — https://github.com/roncoo/roncoo-pay
- Star 约 5.0k；2022-12-31 后停更（代码完整）。
- README 原文证实：「拥有独立的账户体系、用户体系、支付接入体系、支付交易体系、**对账清结算体系**」——这是 GitHub 上**唯一一个在开源版本中自带对账清结算体系**的中文支付系统（经「对账」「reconciliation payment」等关键词多轮检索确认）。
- 对应技术点：8（核心）、5（支付回调）。
- 实现质量：对账模块按「下载渠道对账单 → 解析入库 → 与平台交易逐笔比对 → 差错记录（长款/短款/金额不符）→ 差错处理」的经典流程组织；技术栈偏老（Dubbo 时代），但对账是**数据批处理逻辑**，与框架新旧无关。
- 怎么用最值：精读对账相关的 service 与差错表设计（对账批次、对账差异记录的状态机），把「两方对账」扩展成你要讲的「支付流水 vs 平台订单 vs 库存变更三方对账」——这一步没有现成代码，是你的设计亮点。
- 定级：模块级参考（对账主参考）。

### 2. jeequan/jeepay — https://github.com/jeequan/jeepay
- 核实结论（README 原文）：**对账/清结算能力只在官方托管商业版（计全付）中提及，开源版没有对账模块**；开源版含支付流程、商户体系、渠道配置、回调通知。
- 对应技术点：8 的反面教材——正好在面试中讲「开源支付系统普遍把对账留在商业版，所以我参考 roncoo-pay 自研了对账域」。
- 定级：模块级参考（支付流程，不含对账）。

### 3. Javen205/IJPay（6.6k）/ egzosn/pay-java-parent（3.1k）
- 两者均封装了微信/支付宝的**对账单下载接口**（bill download），可作为你自研对账时拉取渠道对账单的 SDK。
- 定级：模块级参考（工具库）。

### 4. xuxueli/xxl-job / PowerJob（复用）
- 对账是典型 T+1 定时批处理：渠道对账单下载→解析→比对→差错处理，全部挂在调度平台上。
- 定级：生产级参考（组件）。

> 检索备注：GitHub 上「reconciliation + payment + Java」搜索结果全是个位数 star 的学习项目（如 heybadrinath/reconriver 2★、vkrajak/payment-reconciliation-engine 1★），无参考价值；「对账」中文关键词搜索受 GitHub 描述匹配噪音影响大，有效结果只有 roncoo-pay。Gitee 搜索 API 需要鉴权未能使用，roncoo（龙果）主阵地在 Gitee，建议手动在 Gitee 搜「龙果支付」核对最新镜像。

**本节结论**：主参考 roncoo-pay（对账模块精读 + 差错状态机）；辅参考 IJPay/pay-java-parent（对账单下载）+ xxl-job/PowerJob（批处理调度）。三方对账（支付-订单-库存）无任何现成实现，须基于 roncoo-pay 的两方对账模型自行扩展——这正是本项目的差异化爆点。
