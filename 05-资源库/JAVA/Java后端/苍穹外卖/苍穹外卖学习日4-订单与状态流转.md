## 0. 一句话总结

学习日 4 的主体是**订单核心流**：用户下单 → 写 orders + order_detail → 清购物车，以及商家端的**订单状态机**（接单 / 拒单 / 取消 / 派送 / 完成）。
**本日最大的产出不是代码，而是一条"每个操作先校验前置状态"的规则**——它正是阶段门第 4 项（非法状态流转必须被拒绝）的实现。

## 1. 用户下单 `submitOrder()` 六步

| 步 | 动作 | 关键点 |
|---|---|---|
| 1 | 查地址簿，为空抛 `AddressBookBusinessException` | 业务校验放 Service |
| 2 | 查当前用户购物车，为空抛 `ShoppingCartBusinessException` | `userId` 来自 `BaseContext` |
| 3 | `BeanUtils.copyProperties(dto, orders)` + 补默认值，插 orders | **主键回填**拿到 `orders.getId()` |
| 4 | 遍历购物车 → `OrderDetail` → `insertBatch` | 一对多：一条订单 n 条明细 |
| 5 | `deleteByUserId` 清空购物车 | 下单即清车 |
| 6 | 组装 `OrderSubmitVO` 返回（id / orderNumber / orderAmount / orderTime） | **不下发状态**，前端只看这 4 个 |

整段 `@Transactional`：orders、order_detail、shopping_cart 三张表同成同败。

## 2. 订单状态机（核心）

| 码 | 含义 | 可流转到 |
|---|---|---|
| 1 | 待付款 | 2（支付成功）、6（用户取消） |
| 2 | 待接单 | 3（接单）、6（拒单 / 商家取消） |
| 3 | 已接单 | 4（派送）、6（商家取消） |
| 4 | 派送中 | 5（完成） |
| 5 | 已完成 | 终态 |
| 6 | 已取消 | 终态 |

**每个操作的实现套路都一样**（这就是阶段门第 4 项的答案）：

```java
Orders ordersDB = orderMapper.getById(id);
if (ordersDB == null) throw new OrderBusinessException(ORDER_NOT_FOUND);
if (!Orders.TO_BE_CONFIRMED.equals(ordersDB.getStatus()))
    throw new OrderBusinessException(MessageConstant.ORDER_STATUS_ERROR);  // ← 前置状态校验
ordersDB.setStatus(Orders.CONFIRMED);
orderMapper.update(ordersDB);
```

| 操作 | 空校验 | 前置状态校验 | 允许状态 |
|---|---|---|---|
| `rejection` 拒单 | 有 | 有 | 2 待接单 |
| `delivery` 派送 | 有 | 有 | 3 已接单 |
| `complete` 完成 | 有 | 有 | 4 派送中 |
| `userCancelById` 用户取消 | 有 | 有 | 1 或 2 |
| `confirm` 接单 | **无** | **无** | — |
| `cancel` 商家取消 | **无** | **无** | — |

- **实测**：对 status=5 的订单再调 `/admin/order/delivery/{id}` → `{"code":0,"msg":"订单状态错误"}`，且 DB status 仍为 5（**数据未误改**）

### 2.1 已识别缺口：`confirm` / `cancel` 缺守卫（本阶段有意保留）

`confirm()` 既没查单也没判状态 → 对**任意状态**的订单调用都会把它置成 `3`，**终态订单会被"复活"**；`cancel()` 同样两层都缺，且 `ordersDB.getPayStatus()` 在订单不存在时直接 **NPE**。

完整版与本地工程一致，属**上游实现缺口**，非本阶段裁剪造成。根因推测：前端只在该状态下显示按钮，后端便省了守卫——**但前端可被 curl 绕过；前端校验是体验，后端校验才是边界**。

**本阶段决定：不补**，保持与答案代码一致。依据是阶段门第 4 项「非法流转必须被拒绝」已由 `rejection` / `delivery` / `complete` / `userCancelById` 四个方法满足并有实测证据。此缺口属"**已知未修**"，不是"未发现"。

## 4. 本次踩坑：`BeanUtils.copyProperties` 的 null → 基本类型

**现象**：`POST /user/order/submit` 返回 **500**，栈顶为

```
FatalBeanException: Could not copy property 'packAmount' from source to target
  java.lang.IllegalArgumentException: null
    at com.sky.service.impl.OrderServiceImpl.submitOrder(OrderServiceImpl.java:86)
```

**原理**：`OrdersSubmitDTO.packAmount` / `tablewareNumber` 是 `Integer`（可为 null），`Orders` 里是基本类型 `int`。源值为 null 时 Spring 的类型转换器返回 null，塞进 `setPackAmount(int)` 即抛异常。

**为什么参考实现没事**：它依赖"真实小程序前端**永远会传**这几个字段"这个**隐性契约**。测试脚本漏传就炸——这是典型的"源码没错、调用方没守约"。

**修法**（已落在 `OrderServiceImpl.submitOrder`，含注释）：

```java
Orders orders = new Orders();
if (ordersSubmitDTO.getPackAmount() == null)      ordersSubmitDTO.setPackAmount(0);
if (ordersSubmitDTO.getTablewareNumber() == null) ordersSubmitDTO.setTablewareNumber(0);
BeanUtils.copyProperties(ordersSubmitDTO, orders);
```

> **通用教训**：DTO 用包装类型、Entity 用基本类型时，`copyProperties` 一定会在 null 上翻车。要么给默认值，要么两边类型对齐。

## 7. 原理补充：定时任务 / 支付回调 / 异常体系（本阶段未落代码）

### 7.1 定时任务（`com.sky.task.OrderTask`，本工程未导入）

| 方法 | cron | 做什么 |
|---|---|---|
| `processTimeoutOrder` | `0 * * * * ?`（每分钟） | 查 `status=1 且 order_time < now-15min` → 置 **6 已取消**，原因"订单超时，自动取消" |
| `processDeliveryOrder` | `0 0 1 * * ?`（每天 01:00） | 查 `status=4 且 order_time < now-60min` → 置 **5 已完成** |

**关键理解（最容易记错的一点）**：「15 分钟」**不在 cron 里，而在 SQL 条件里**。cron 管"多久扫一次"，SQL 管"扫谁"。所以是每分钟轻扫一遍，而不是每 15 分钟才找一次——后者最坏让用户多等 15 分钟才被取消。

**不严谨处**：第二条用 `order_time` 而非 `delivery_time` 做比较，严格说应看"进入派送中的时间"。清昨日烂尾单够用，但语义不精确。

**开关**：需要启动类上的 `@EnableScheduling`，否则 **编译通过、启动正常、永不触发**——与 `@CacheEvict` 缺 `@EnableCaching` 属同一类静默失效。经验：注解不生效，先查 `@EnableXxx`。

> Spring 的 cron 是 **6 段**（秒 分 时 日 月 周），比 Linux 的 5 段多一个「秒」。

### 7.2 微信支付回调 `paySuccess(outTradeNo)`

由微信**异步回调**触发（**不是** HTTP 接口的返回值——前端 `payment()` 只是唤起收银台）：

```
按 number + userId 查单
  → 置 status=2 待接单 / payStatus=1 已支付 / checkoutTime=now
  → WebSocket 推 {type:1, orderId, content} → 商家端「来单提醒」
```

**这解释了本阶段为何测试时要手工 `update orders set status=2`**——支付被砍后，「待付款 → 待接单」的触发器缺失。不是偷懒跳过，是补触发器。

### 7.3 异常体系

```
业务异常（OrderBusinessException / AddressBookBusinessException / SetmealEnableFailedException …）
  └─ extends BaseException extends RuntimeException
        └─ GlobalExceptionHandler（@RestControllerAdvice）统一兜底
              └─ log.error("异常信息：{}", msg) + Result.error(msg) → {"code":0,"msg":"…"}
```

- Service **只管抛**，完全不认识 HTTP；Controller **不写 try-catch**；异常统一由全局处理器翻译
- 所以业务异常返回 `code:0` 而不是 500；**业务异常走 Result，系统异常才走 500**，是两条路
- 另有 handler 把 SQL 的 `Duplicate entry 'x' for key ...` **按空格切出用户名**，拼成"x 已存在"——比把整条 SQL 报错甩给用户友好得多

> **更正**：非法流转抛的是 `OrderBusinessException(MessageConstant.ORDER_STATUS_ERROR)`，**不是** `OrderStatusErrorException`（`sky-common/exception/` 下无此类）。"订单状态错误"是**消息内容**，不是类名。
