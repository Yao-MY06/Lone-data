## 0. 一句话总结

**缓存的核心矛盾是「内存不能无限大」和「数据一致」之间的拉扯。**
骨架四块：**一条基础流程**（查缓存 → 未命中查库 → 写回）撑起一切；**三个问题**分别是"都不存在"（穿透）、"热点失效"（击穿）、"批量失效"（雪崩）；**两个解法**代表两种取舍——互斥锁拿性能换一致，逻辑过期拿一致换性能；**一个封装**（`CacheClient`）把三套逻辑抽成通用工具。

## 1. 块 A · 基础流程（2.1–2.4）

### 1.1 标准读流程

```
请求 → 查 Redis → 命中就返回
                未命中 → 查数据库 → 查到 → 写回 Redis（带 TTL）→ 返回
                                  查不到 → 返回 404   ← ❗️「缓存穿透」的入口
```

### 1.2 缓存更新策略：三选一

| 策略 | 谁来做 | 特点 |
|---|---|---|
| **内存淘汰** | Redis 自动 | 达到 `maxmemory` 按策略淘汰，不可控 |
| **超时剔除** | Redis 自动 | 设 TTL 到期自动删，**兜底** |
| **主动更新** | 你写代码 | 改数据时手动删缓存，**一致性最好** |

**项目选：主动更新 + 超时剔除兜底。**

### 1.3 双写一致：两个选择题（重点）

**① 删除缓存，还是更新缓存？→ 删缓存**
每次改库都更新缓存的话，**中间没人来查**时那些更新全是无效写。删掉更省——下次有人查时自然重建（懒加载）。

**② 先操作数据库，还是先操作缓存？→ 先操作数据库，再删缓存**
顺序不能反。若**先删缓存**：

```
线程1: 删缓存
线程2: 查缓存 → 没有 → 查库（旧值）→ 写入缓存（旧值！）
线程1: 更新数据库（新值）
结果: 缓存=旧值、库=新值，且一直错到 TTL 到期
```

反过来"先改库再删缓存"，最坏只是**极短时间**内有人读到旧值，下次查询即修正。

### 1.4 2.4 的实现就两条

- 查不到 → 查库 → 写缓存**并设 TTL**
- 改数据 → 先改库 → **再删缓存**

## 2. 块 B · 三大缓存问题（2.5–2.8）

| | 穿透 | 击穿 | 雪崩 |
|---|---|---|---|
| **触发** | 缓存和库**都没有** | **一个**热点 key 失效 | **大批** key 同时失效 |
| **后果** | 请求全打到数据库 | 并发瞬间打库 | 大量请求打库 |
| **解法①** | 缓存空对象 | 互斥锁 | TTL 加随机值 |
| **解法②** | 布隆过滤器 | 逻辑过期 | 集群 / 降级 / 多级缓存 |

### 2.1 穿透的两种解法对比

- **缓存空对象**：库里查不到 → 往 Redis 写空值（`""`）。**实现简单**，缺：多占内存 + 短期不一致。**项目选它。**
- **布隆过滤器**：位数组 + 哈希判断 key 是否存在，判不存在直接挡掉。**省内存**，缺：**实现复杂 + 有误判**（哈希冲突）。归**候选技术池**。

### 2.2 代码里最容易搞混的两行 ⭐

```java
String shopJson = stringRedisTemplate.opsForValue().get(key);
if (StrUtil.isNotBlank(shopJson)) {        // ① 命中且有真实数据 → 反序列化返回
    return JSONUtil.toBean(shopJson, Shop.class);
}
if (shopJson != null) {                     // ② 命中但是空字符串 → 是防穿透写的空值
    return null;                            //    直接告诉调用方"不存在"，不再查库
}
// 走到这里才是真正的「缓存未命中」
```

**判断顺序和语义必须看懂**：`isNotBlank` 管"有真数据"，`!= null` 管"命中但是空值"。

## 3. 块 C · 击穿的两个解法（2.9、3.0）

| | 互斥锁方案 | 逻辑过期方案 |
|---|---|---|
| **核心做法** | 只让一个线程去查库 | 不设 TTL，过期时间存在 value 里 |
| **其他线程** | 排队等待（sleep 重试） | 不等，直接返回旧数据 |
| **一致性** | 始终一致 | **重建完成前返回脏数据** |
| **代价** | 串行、性能差、有死锁风险 | 实现复杂，且**必须预热** |

### 3.1 互斥锁 —— 用 `SETNX` 当锁

```java
private boolean tryLock(String key) {
    Boolean flag = stringRedisTemplate.opsForValue().setIfAbsent(key, "1", 10, TimeUnit.SECONDS);
    return BooleanUtil.isTrue(flag);
}
private void unlock(String key) { stringRedisTemplate.delete(key); }
```

`SETNX`（学习日 1 学过：键存在就返回 0 且**不改原值**）正好做锁。拿到锁的查库 + 重建；没拿到的 `sleep(50)` 递归重试 → **并行查询变串行**。

### 3.2 逻辑过期 —— 把过期时间写进 value

```java
@Data
public class RedisData {          // 包一层，不改原 Shop 实体（无侵入）
    private LocalDateTime expireTime;
    private Object data;
}
```

判断 `expireTime`：没过期直接返回；**过期了开独立线程重建，自己立刻返回旧数据**。其他线程完全不等 → 代价是**重建完成前读到脏数据**。

> ⚠️ **必须预热**：key 永不失效，若一开始 Redis 里就没这个 key，`queryWithLogicalExpire` 第一步 `StrUtil.isBlank(json)` 直接 `return null`——**永远不查库**。所以项目写了 `saveShop2Redis`，用单元测试把数据灌进去。

## 4. 块 D · 封装 `CacheClient`（3.1）—— 最值得学的一节

### 4.1 关键设计：泛型 + 函数式回调

```java
public <R, ID> R queryWithPassThrough(
        String keyPrefix, ID id, Class<R> type,
        Function<ID, R> dbFallback,        // ← 把"怎么查库"交给调用方
        Long time, TimeUnit unit) {
    ...
    R r = dbFallback.apply(id);             // 回调，不关心查 Shop 还是 Voucher
    ...
}
```

**工具类只负责缓存逻辑**（查缓存 / 判空值 / 加锁 / 写回），**不关心具体查哪张表**——`Function<ID, R>` 由调用方传入。一个工具类服务所有业务。

### 4.2 调用处：三行注释就是策略开关

```java
Shop shop = cacheClient.queryWithPassThrough(CACHE_SHOP_KEY, id, Shop.class,
        this::getById, CACHE_SHOP_TTL, TimeUnit.MINUTES);          // 防穿透

// Shop shop = cacheClient.queryWithMutex(...);                     // 互斥锁防击穿
// Shop shop = cacheClient.queryWithLogicalExpire(..., 20L, TimeUnit.SECONDS);  // 逻辑过期防击穿
```

**复习时看这一段就够**：注释掉哪两行、留下哪一行 = 这个业务用哪种策略。

## 5. 讲义里的两个代码 bug（真跑必改）

| 位置 | 问题 |

| 2.9 `queryWithMutex` | `stringRedisTemplate.opsForValue().get("key")` —— **写死了字符串 `"key"`** 而不是变量 `key`，真跑永远查不到缓存 |
