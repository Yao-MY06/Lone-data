## 0. 一句话总结

**秒杀的核心是两个并发问题：库存超卖、一人一单。**
超卖用**乐观锁**（把"判断 + 扣减"合并成一条带条件的 UPDATE）；一人一单用**悲观锁**（插入数据没有旧值可比）。
单机 `synchronized` 能解决，但**集群下 JVM 不同就失效** → 必须用**分布式锁**。
分布式锁的四步演进，每一步都是被上一步的漏洞逼出来的：**加锁 → 误删 → 原子性 → 续期**。

## 1. 全局唯一 ID（3.1–3.2）

**为什么不用数据库自增**：① ID 规律太明显，对手能反推销量；② 单表容量有限，分库分表后 ID 不能重复。

**64 位结构**：

| 位段 | 长度 | 含义 |
|---|---|---|
| 符号位 | 1 bit | 永远 0（保证正数） |
| 时间戳 | 31 bit | 以秒为单位，可用约 69 年 |
| 序列号 | 32 bit | 秒内计数器，每秒可产生 2³² 个不同 ID |

```java
long timestamp = nowSecond - BEGIN_TIMESTAMP;               // 2022-01-01 起
String date = now.format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));
long count = stringRedisTemplate.opsForValue().increment("icr:" + keyPrefix + ":" + date);
return timestamp << COUNT_BITS | count;                     // 左移 32 位后按位或
```

**三个设计点**：
1. `<< 32 | count` 位运算拼接 → ID 整体递增且同秒内不重复。
2. **序列号 key 按天分片**（`icr:order:2026:10:16`）→ 否则单 key 无限增长。
3. `CountDownLatch` 测试技巧：开 300 线程各生成 100 个 ID，`latch.await()` 让主线程等全部跑完再统计耗时。

## 2. 秒杀下单与超卖（3.3–3.6）

**表结构分两张**：`tb_voucher`（券的基本信息）+ `tb_seckill_voucher`（**特价券才需要**：库存、起止时间）。

**下单五步**：查券 → 判开始时间 → 判结束时间 → 判库存 → 扣库存 + 建订单。

### 2.1 超卖怎么发生

```
初始 stock = 1
线程1 读到 stock = 1
线程2 读到 stock = 1     ← 两个线程读到同一个 1
线程1 判断 1 > 0 通过 → 扣减 → 0
线程2 判断 1 > 0 通过 → 扣减 → -1   ← 超卖
```

根因：**"查-判-扣"三步不是原子的。**

### 2.2 乐观锁：两种写法差别很大

**方案一（失败率极高）**：校验前后库存一致
```java
.eq("voucher_id", voucherId).eq("stock", voucher.getStock())
```
100 个线程都读到 `stock=100`，都带 `stock=100` 去扣——**只有第 1 个能成功**。

**方案二（实用）**：只要求 `stock > 0`
```java
.eq("voucher_id", voucherId).gt("stock", 0).update()
```

> 🕳️ **讲义 bug**：讲义写成 `.eq("voucher_id", voucherId).update().gt("stock", 0)` —— **`.gt()` 放在 `update()` 之后**，链式顺序错，真跑抛异常。

## 3. 一人一单（3.6'）—— 三个连环坑

**需求**：同一张券一人一单。查 `count > 0` 即拒绝。

**为什么这里不能用乐观锁**：**乐观锁适合更新数据，这里是插入数据**——插入没有旧值可比，只能用悲观锁。

**坑① 锁粒度太粗**
```java
public synchronized Result createVoucherOrder(...)    // ❌ 所有用户互相排队
synchronized(userId.toString().intern()) { ... }       // ✅ 只锁同一用户
```
**为什么要 `intern()`**：`userId.toString()` 每次都是新 String 对象，不 `intern` 则同一用户拿到**两个不同锁对象** = 没锁。`intern()` 从常量池取，保证同一 userId 同一把锁。

**坑② 锁必须在事务外层**
锁在 `@Transactional` 方法**内部** → **事务未提交锁已释放** → 下一个线程查不到订单 → 又下一单。

**坑③ `this.` 调用不走代理**
```java
synchronized(...) { return createVoucherOrder(voucherId); }         // ❌ 事务失效
IVoucherOrderService proxy = (IVoucherOrderService) AopContext.currentProxy();
return proxy.createVoucherOrder(voucherId);                          // ✅ 走代理
```
同类规律：学习日 3 的 `@CacheEvict` 因缺 `@EnableCaching` 静默失效。**注解不生效 → 先查代理与开关。**

## 4. 集群锁失效 → 分布式锁（3.7、4.1–4.2）

两台 tomcat = **两个独立 JVM**。`synchronized` 锁对象代码一样但**不是同一对象** → A 内部互斥、B 内部互斥，**A 与 B 不互斥**。

**分布式锁定义**：满足分布式/集群模式下**多进程可见且互斥**的锁。
**五个条件**：可见性 / 互斥 / 高可用 / 高性能 / 安全性。
**三种实现**：MySQL（性能差）/ **Redis（`SETNX`，本课程）** / Zookeeper。

## 5. 分布式锁的四步演进（4.3–4.8）⭐ 全章精华

| 步 | 做法 | 解决什么 / 暴露什么 |
|---|---|---|
| ① | `setIfAbsent(key, threadId, timeoutSec, SECONDS)` | 互斥（`SETNX` 原子）+ 过期时间防死锁 |
| ② | value 存 `UUID + 线程id`，删除前先 `get` 比对 | 解决**误删别人的锁**（自己阻塞超时→锁释放→别人拿到→自己恢复后 delete） |
| ③ | **Lua 脚本**：`GET` 比对 + `DEL` 合成一次执行 | 解决**原子性**（比对通过后、delete 前锁到期 → 仍会误删） |
| ④ | 遗留：**锁不住**（业务超时） | 解法：**续期** → 学习日 6 的 Redisson 看门狗 |

**为什么 value 要带 UUID**：集群下两个 JVM 的线程 id 可能都是 `1`，需标识"哪个 JVM 的哪个线程"。

### Lua 解锁脚本

```lua
if (redis.call('GET', KEYS[1]) == ARGV[1]) then
  return redis.call('DEL', KEYS[1])
end
return 0
```

```java
private static final DefaultRedisScript<Long> UNLOCK_SCRIPT;
static {
    UNLOCK_SCRIPT = new DefaultRedisScript<>();
    UNLOCK_SCRIPT.setLocation(new ClassPathResource("unlock.lua"));
    UNLOCK_SCRIPT.setResultType(Long.class);
}
public void unlock() {
    stringRedisTemplate.execute(UNLOCK_SCRIPT,
            Collections.singletonList(KEY_PREFIX + name),   // → KEYS
            ID_PREFIX + Thread.currentThread().getId());     // → ARGV
}
```

**必须记住的唯一 API 细节**：`execute(脚本, KEYS 列表, ARGV...)` —— `KEYS[1]` 是锁 key，`ARGV[1]` 是线程标识。Lua 在 Redis 内**原子执行**，执行期间不被插队。
